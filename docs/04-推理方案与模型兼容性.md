# 推理方案与模型兼容性

> 目标：**x86 和 Zynq 用同一套业务代码，能跑从 PyTorch / TensorFlow / Paddle 训练出来的模型。**
> 本文给出技术路线、实测结果、Zynq 的真实能力边界，以及一份"模型接不进来时怎么查"的清单。

---

## 1. 先说清楚一件事：Zynq-7000 能跑什么模型

这一点必须先摆出来，否则"兼容各种模型"会变成不切实际的期待。

Zynq-7000 的 PS 是双核 Cortex-A9，主频 667MHz~1GHz，NEON 128-bit SIMD，**没有 fp16 硬件**。

按 NEON 每周期 4 个单精度乘加、1GHz 估算，理论峰值约 8 GFLOPS；考虑内存带宽（DDR3-1066，实际可用 1~2 GB/s）和访存开销，**实际有效算力大约 0.5~1.5 GFLOPS**。

| 模型 | 典型计算量 | Cortex-A9 估算 | 结论 |
|---|---|---|---|
| MobileNetV2 224×224 | ~0.6 GFLOPs | 0.5~1.5 s | 可行，需量化 |
| MobileNetV3-Small | ~0.12 GFLOPs | 0.1~0.3 s | 推荐 |
| SqueezeNet 1.1 | ~0.7 GFLOPs | 0.5~1.5 s | 可行 |
| ResNet-18 224×224 | ~3.6 GFLOPs | 3~8 s | 勉强 |
| YOLOv5n 640×640 | ~9 GFLOPs | 10~30 s | 不可用 |
| 任何 ViT / BERT-base | 数十 GFLOPs | 分钟级 | 不可行 |

**结论**：Zynq-7000 适合"小模型 + 低分辨率 + 低频调用"的场景（分拣、状态识别、简单检测）。
如果是 ZynqMP（Cortex-A53 ×4，1.5GHz，有 fp16），上述数字可以再快 4~8 倍，YOLO 系列才有实用价值。

> 这张表是数量级估算，不是基准测试。**上板第一件事应该是实测**（用 `model_inspect --bench` 的同一套代码）。

---

## 2. 模型来源与转换路径

所有训练框架的产物最终统一成 **ONNX**，这是唯一能在 x86 和 ARM 之间共享的中间格式。

| 训练框架 | 转换方式 | 注意事项 |
|---|---|---|
| PyTorch | `torch.onnx.export(model, dummy, "m.onnx", opset_version=17, dynamic_axes={...})` | `dynamic_axes` 决定 batch/序列维是否动态；`opset_version` 建议 17（ORT 1.23 支持到 21） |
| TensorFlow / Keras | `tf2onnx` | 注意 NHWC 布局，很多 TF 模型导出后输入是 NHWC |
| PaddlePaddle | `paddle2onnx` | Paddle 的 `paddle.nn.functional` 有些算子需要 opset ≥ 11 |
| YOLO 系列 | ultralytics 自带 `export(format='onnx')` | 输出通常是 `[1, 84, 8400]` 这种"未解码"格式，后处理要自己写 |

**训练侧必须做对的两件事**：

1. **导出时固定或声明动态维**，否则部署端不知道能喂多大的数据；
2. **把预处理参数一起交付**（归一化均值/方差、色彩顺序、输入尺寸、letterbox 策略）。
   实测中"模型跑通了但结果全错"的原因，80% 是预处理和训练时不一致。

## 3. 兼容性实测（本次验证）

`tools/gen_test_models.py` 生成 7 种典型形态的模型，用 `tools/model_inspect` 逐个验证。
全部通过（MSVC + ONNX Runtime 1.23.2）：

| 模型 | 形态 | 验证点 | 结果 |
|---|---|---|---|
| `dyn_batch.onnx` | 输入 `[-1,4]` | 动态 batch 维 | ✅ `1.1 / 0.3`（与手算一致） |
| `multi_io.onnx` | 2 进 2 出 | 多端口 + 命名匹配 | ✅ `sum=1` `diff=0` |
| `int64_input.onnx` | `i64[1,8]` | NLP 式整型输入 + Cast | ✅ `0.01` |
| `fp16_io.onnx` | `f16` 进 `f16` 出 | 半精度端到端 | ✅ `1.5`（0.5+1.0） |
| `u8_input.onnx` | `u8[1,3,8,8]` | 图像式无符号输入 | ✅ `1/255` |
| `small_cnn.onnx` | Conv/BN/ReLU/Pool/GAP/Gemm | 真实 CNN 算子链 | ✅ `[1,10]` 正常输出 |
| `softmax_1d.onnx` | `f32[4]` 一维 | 一维输入边界情况 | ✅ 均匀输入 → 0.25 |

这些覆盖了部署时最常踩的坑：动态维、多 IO、整型输入、半精度、图像输入。

> 补充：`small_cnn` 在 x86 上单线程 **0.034 ms/次**。这个数字只用来做基线对比，
> 不能直接推算 ARM 性能（架构、内存带宽、指令集都不同）。

## 4. 后端选型

| 后端 | 算子覆盖 | armv7 | 体积 | 动态形状 | 量化 | 结论 |
|---|---|---|---|---|---|---|
| **ONNX Runtime** | ★★★★★ | 需自行交叉编译 | 中（~10-30MB） | ✅ | ✅ QDQ/Int8 | **主选** |
| MNN（阿里） | ★★★★☆ | 官方支持 | 小 | 部分 | ✅ | 备选 |
| ncnn（腾讯） | ★★★☆☆ | 优秀 | 极小 | 弱 | ✅ | CV 专用备选 |
| TFLite | ★★★☆☆ | 支持 | 小 | 部分 | ✅ | 需要额外转换 |
| OpenCV DNN | ★★☆☆☆ | 支持 | 中 | 弱 | 有限 | 不推荐做主力 |

**决策**：

- **x86（Windows/Linux）**：ONNX Runtime，开箱即用（已有预编译包）。
- **armv7（Zynq-7000）**：优先自己交叉编译 ONNX Runtime（见 §5）。这样模型只需导出一次，
  两边跑的是同一个运行时、同一套算子实现，**数值行为一致**，调试成本最低。
- **备选**：如果 ORT 在板子上体积/内存吃不住，再接 MNN 或 ncnn 后端。
  由于 `my::infer` 是后端抽象的，接入新后端不影响任何业务代码（见 `docs/02-API设计.md` §5）。

> 为什么不用 ncnn 作为主方案：ncnn 的 ONNX 转换（`onnx2ncnn`）遇到不支持的算子会直接失败，
> 而"各种训练好的模型"恰恰意味着算子不可控。ORT 的算子覆盖是这几种里最全的。

## 5. ONNX Runtime 的 armv7 交叉编译

### 5.1 为什么必须在 Linux 里编

ORT 的构建系统（`tools/ci_build/build.py`）假定 **Linux 宿主 → Linux ARM 目标**，
官方不支持 mingw 宿主交叉编译。所以用 WSL2（Ubuntu 24.04）。

### 5.2 一个关键的巧合：glibc 版本对上了

| 环境 | glibc | libstdc++ |
|---|---|---|
| PetaLinux 2020.2 sysroot（本板） | **2.30** | 6.0.27（GCC 9.2） |
| Ubuntu 24.04 armhf（构建宿主，**不要用于本板**） | **2.39** | 6.0.32（GCC 13.2） |

两边版本**不一致**（本板 2.30 / Ubuntu 2.39）：Ubuntu 工具链编出来的 `.so` 在板上会报 `GLIBC_2.38 not found`，
**不需要**把 PetaLinux 的 sysroot 搬进 WSL。

> 如果目标板是更老的 PetaLinux（比如 glibc 2.31），就必须把 `CMAKE_SYSROOT`
> 指向板子自己的 sysroot 再编，否则会报 `GLIBC_2.xx not found`。

### 5.3 构建脚本

`scripts/build-ort-armv7-wsl.sh`，在 Windows 上一行命令启动：

```powershell
wsl -d Ubuntu-24.04 -u root -- bash /mnt/d/.../scripts/build-ort-armv7-wsl.sh
```

脚本做的事：

1. 自动探测 Windows 宿主代理（WSL2 NAT 下 127.0.0.1 不可达，要用默认网关 IP）；
2. `apt install` 交叉工具链 + Python 依赖；
3. clone ORT `v1.23.2`（含子模块）；
4. 生成 `armv7-toolchain.cmake`（`-march=armv7-a -mcpu=cortex-a9 -mfpu=neon -mfloat-abi=hard`）；
5. `./build.sh --config Release --build_shared_lib --parallel --skip_tests`；
6. 收集 `libonnxruntime.so` + 头文件到 `/opt/ort-build/install`，并打印产物所需的最高 GLIBC 符号版本。

### 5.4 已经踩到的坑

| 现象 | 原因 | 解法 |
|---|---|---|
| `build.py: error: ambiguous option: --arm` | **ORT 1.23 删除了 `--arm`/`--arm64` 参数**，交叉编译完全由 `CMAKE_TOOLCHAIN_FILE` 驱动 | 去掉 `--arm`，只传 toolchain file |
| `Running as root is not allowed` | build.py 的安全检查 | `--allow_running_as_root` |
| clone 卡在 13MB 十分钟 | WSL2 NAT 下访问不了 Windows 的 `127.0.0.1:7897` 代理 | 用默认网关 IP `172.x.x.1:7897` 设置 `http_proxy` |
| `cannot find crt1.o`（aarch64 时遇到） | ARM GNU Toolchain 的 sysroot 在 `<prefix>/libc` | 见 `docs/03` §3.3 |

### 5.5 产物接入

编好之后，Windows 侧只需：

```powershell
cmake --preset linux-armv7 -DMYLIB_ONNXRUNTIME_ROOT=D:/path/to/install
```

`cmake/Deps.cmake` 里已经写好了判定逻辑：只要 `include/onnxruntime_cxx_api.h` 和
`lib/libonnxruntime.so` 都在，`MYLIB_INFER_BACKEND` 就会变成 `onnxruntime`，
armv7 构建会自动链接它 —— **业务代码一行不用改**。

### 5.6 实测结果（已验证）

构建产物（`libonnxruntime.so.1.23.2`，20 MB）：

```
ELF 32-bit LSB shared object, ARM, EABI5, hard-float
NEEDED: libstdc++.so.6, libm.so.6, libgcc_s.so.1, libc.so.6, ld-linux-armhf.so.3
SONAME: libonnxruntime.so.1
最高 GLIBC 符号:   2.38   （本板 2.30 ❌，所以板上改用 1.18.1）
最高 GLIBCXX 符号: 3.4.30 （本板 3.4.27 ❌）
```

接入本项目后，armv7 产物：

```
bin/model_inspect      ELF 32-bit ARM (machine 0x28), NEEDED libonnxruntime.so.1
bin/example_pipeline   ELF 32-bit ARM, 0.62 MB（ORT 走动态库，程序本身很小）
```

**结论：交叉编译 + 链接 + ABI 版本核对全部通过，并且已在 Zynq-7020 实机跑通**
（见 [06-板端验证手册](06-板端验证手册.md)）。

### 5.7 部署到板子

```bash
# 板子上需要三样东西：
scp libonnxruntime.so.1 root@<board>:/usr/lib/        # SONAME 文件名，不能改名
scp model_inspect      root@<board>:/tmp/
scp small_cnn.onnx     root@<board>:/tmp/

# 板上
ldconfig       # 或 export LD_LIBRARY_PATH=/usr/lib
/tmp/model_inspect /tmp/small_cnn.onnx --run --bench 10
```

> 注意 SONAME 是 `libonnxruntime.so.1`。如果只拷了 `libonnxruntime.so`，
> 运行时会报 `error while loading shared libraries: libonnxruntime.so.1`。
> 这是最容易踩的一个坑。

## 6. ncnn 后端（已接入，作为备选）

### 6.1 什么时候用它

| 场景 | 选 ORT | 选 ncnn |
|---|---|---|
| 模型算子五花八门，不想被转换卡住 | ✅ | |
| Zynq 上要极致小体积 | | ✅ |
| 常规 CNN（分类 / 轻量检测） | | ✅ |
| 需要 fp16/int8 量化在 ARM 上跑得动 | ✅ | ✅ |
| 只有 ONNX 模型、不想维护转换链 | ✅ | |
| 板端内存紧张（ncnn 静态库 3.9MB） | | ✅ |

两个后端**可以同时编译进同一个二进制**，运行期按模型扩展名或显式指定来挑：

```cpp
// .onnx  -> onnxruntime（找不到才用 ncnn）
// .param -> ncnn（找不到才用 onnxruntime）
my::infer::Options opt;
opt.model_path = "model.param";
auto s = my::infer::create_session(opt);   // 自动选 ncnn

// 也可以强制
opt.backend = "ncnn";
```

### 6.2 转换链：onnx2ncnn

ncnn 用自己的 `.param`（文本结构）+ `.bin`（裸权重）格式，转换靠 `onnx2ncnn`。

**为什么在 WSL 里编工具**：`onnx2ncnn` 需要 protobuf。Linux 上 `apt install protobuf-compiler
libprotobuf-dev` 一行搞定，Windows 上要自己编 protobuf 或用 vcpkg。转换本来就是宿主机上的
离线步骤，Linux 二进制完全够用。

```powershell
# 一次性构建工具（约 2 分钟）
wsl -d Ubuntu-24.04 -u root -- bash scripts/build-ncnn-tools-wsl.sh

# 单个模型
wsl -d Ubuntu-24.04 -u root -- /opt/ncnn-tools/ncnn-build/tools/onnx/onnx2ncnn \
    model.onnx model.param model.bin

# 批量（会打印每个模型能否转换）
wsl -d Ubuntu-24.04 -u root -- bash scripts/convert_all_models.sh
```

### 6.3 转换能力实测（8 个测试模型）

| 模型 | 结果 | 说明 |
|---|---|---|
| `small_cnn` | ✅ | Conv / ReLU / MaxPool / GlobalAveragePool / Flatten / Gemm 全支持 |
| `multi_io` | ✅ | Add / Sub → `BinaryOp` |
| `dyn_batch` | ✅ | MatMul → `InnerProduct`（动态 batch 退化为 1） |
| `softmax_1d` | ✅ | |
| `identity_1x1x4` | ⚠️ | `Identity` 不支持（实际模型里可以删掉这层） |
| `int64_input` | ❌ | `Cast` 不支持——**int64 整型输入是 ncnn 的弱项** |
| `u8_input` | ❌ | 同上 |
| `fp16_io` | ❌ | 能转出文件，但 `load_model` 失败 |

结论很清楚：**常规 CNN 没问题，NLP/整型输入/类型转换类的模型要小心。**

### 6.3.1 真实模型验证：MobileNetV2

只测自己造的模型不够，所以拿官方模型库里的 `mobilenetv2-12.onnx`（13.3 MB）试了一次：

| 后端 | 结果 |
|---|---|
| **ONNX Runtime** | ✅ 正常，输入 `[-1,3,224,224]`，x86 单线程 **13.9 ms/次** |
| **ncnn** | ❌ `onnx2ncnn` 报 `Shape not supported yet!`，转出来的 `.param` 加载时 ncnn 直接崩溃 |

把动态 batch 固定成 1 之后（`tools/staticize_onnx.py`）仍然报 `Shape not supported` ——
原因是模型图里本身就有 `Shape` 节点（动态 reshape 用的），这是个**图结构层面的不兼容**，
不是"把形状写死"能解决的。

**这条结论很重要**：onnx2ncnn 能对付的是"导出得比较干净的 CNN"，
而官方模型库里的预训练模型经常带动态 reshape / Shape / Cast，转不过去很正常。

> ncnn 官方自己也承认这一点——`onnx2ncnn` 每次启动都会提示
> "may not fully meet your needs, please use PNNX"。
> PNNX 走的是 **PyTorch → ncnn** 的路子，需要原始 `.pt` 模型，不能从 ONNX 转。

**实践建议**：

- 模型只在 ONNX 一层维护（尤其是动态 batch 的）→ **用 ORT**；
- 确定要上 ncnn → 从 PyTorch 侧用 PNNX 导出，而不是 ONNX 转；
- 用 `scripts/convert_all_models.sh` 批量试转，它会把有警告的产物**直接删掉**，
  免得拿着一个注定跑不起来的 `.param` 去调半天。

### 6.4 数值一致性验证

工具：`tools/compare_outputs.py`（对比 `model_inspect --dump` 导出的两个后端输出）。

```powershell
model_inspect models\small_cnn.onnx       --run --dump output\a.txt          # ORT
model_inspect models\ncnn\small_cnn.param --run --shape 1,3,32,32 --dump output\b.txt  # ncnn
python tools\compare_outputs.py output\a.txt output\b.txt
```

实测：

| 模型 | max_abs | 判定 |
|---|---|---|
| small_cnn（Conv/ReLU/Pool/GAP/Gemm） | **2.98e-08** | 一致（fp32 舍入级） |
| multi_io（Add/Sub） | **0** | 逐位一致 |

这个误差量级说明两边算的是同一件事，不是"看起来差不多"。

### 6.5 两个非踩不可的坑

**坑 1：ONNX 的 `Conv` 节点必须显式写 `kernel_shape`。**

ONNX 里 `kernel_shape` 是可选属性（可由权重形状推断），ONNX Runtime 不在乎；
但 `onnx2ncnn` 读的就是这个属性，缺了就生成 `kernel_w = 0`，
ncnn 推理时算 `(w - kernel)/stride` → **整数除零，进程直接崩（0xC0000094）**，
而且没有任何错误信息——我们第一次就是这么崩的。

> 训练侧导出时务必确认 Conv 带 `kernel_shape`。PyTorch 的 `torch.onnx.export` 默认会写，
> 手写 ONNX 图（比如我们的测试生成器）容易漏。

**坑 2：ncnn 的 `Mat` 通道步长 `cstep` 会按 16 字节对齐补齐。**

`Mat(3,1,1)` 的 `cstep` 是 4 而不是 3，不能把它当成紧凑的 `w*h*c` 数组直接 `memcpy`。
封装层做了两件事：

- 输入：按通道逐通道拷贝（`Mat::channel(q)`），不用整块 memcpy；
- 输出：统一重排成紧凑的 `std::vector<float>` 再交给调用方，
  顺带解决了"输出内存由谁持有"的问题。

### 6.6 armv7 交叉编译

ncnn 的交叉编译比 ORT 简单得多（十分钟级别）：

```powershell
cmake -S third_party/ncnn-src -B build/ncnn-armv7 -G Ninja `
  -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/linux-armv7-zynq.cmake `
  -DCMAKE_BUILD_TYPE=Release `
  -DNCNN_VULKAN=OFF -DNCNN_SHARED_LIB=OFF -DNCNN_OPENMP=OFF `
  -DNCNN_BUILD_TOOLS=OFF -DCMAKE_INSTALL_PREFIX=third_party/ncnn-linux-armv7-20250503
cmake --build build/ncnn-armv7 --target install
```

产物：`libncnn.a`，**3.9 MB**（静态）。
接进本项目后 armv7 的 `model_inspect` 是 2.9MB（ncnn 静态 + ORT 动态）。

> 静态库认架构的坑：`.a` 是 ar 归档，前面有 100KB+ 的符号表，
> 不能只看文件开头判断架构。`cmake/Deps.cmake` 里的 `_mylib_elf_arch()`
> 会分块扫描找 ELF 魔数。

### 6.7 体积对比（实测）

| 产物 | ORT 动态 | ncnn 静态 |
|---|---|---|
| armv7 应用增量 | +90 KB（.so 单独 20MB 部署） | +2.9 MB |
| armv7 库文件 | libonnxruntime.so **20 MB** | libncnn.a **3.9 MB** |
| Windows MSVC | onnxruntime.dll 14 MB + .lib | ncnn.lib 23 MB（静态） |

板端 rootfs 紧张时，ncnn 的体积优势明显；但 ORT 的算子覆盖是拿体积换来的。

## 7. 模型接入检查清单

一个陌生模型跑不起来时，按这个顺序查，通常前三条就能定位问题。

1. **先跑 `model_inspect <model>`**
   能不能加载？输入输出名字/类型/形状对不对？动态维是哪个？

2. **再看 `--run` 的输出**
   能不能跑通？输出有没有 NaN/Inf？量级是否合理（分类 logits 一般 -20~20）？

3. **核对预处理**
   - 色彩顺序：训练用 RGB 还是 BGR？（OpenCV 读图默认 BGR）
   - 归一化：`/255`？还是 `(x-mean)/std`？mean/std 是每通道还是标量？
   - 布局：NCHW 还是 NHWC？
   - resize：直接拉伸、还是保持宽高比 + padding（letterbox）？

4. **核对输出解码**
   - 分类：要不要先 softmax？
   - 检测：输出是 `[N, 84, 8400]` 还是已解码的 `[N, 6]`？
   - 分割：是 logits 还是 argmax 后的类别图？

5. **算子支持**
   ORT 报 `NOT_IMPLEMENTED` / `No OpKernel registered` → 该算子不在 CPU EP 里。
   升级 ORT 版本、改用等价算子、或把这一段用 `onnxruntime-extensions` 自定义算子实现。

6. **opset 版本**
   ORT 1.23 支持到 opset 21。模型 opset 过高时要么降 opset 重导，要么升级 ORT。

7. **动态形状**
   导出时如果没写 `dynamic_axes`，batch 就是固定的 1。喂 batch=8 会直接报错。

8. **量化模型**
   用 QDQ 格式（`QuantizeLinear`/`DequantizeLinear`）导出，ORT 会自动走 Int8 kernel。
   旧的 `QLinearConv` 风格也能跑，但转换链更脆。

9. **精度差异**
   同一个模型 x86 和 ARM 的输出差多少？fp32 下通常 `1e-6` 量级；
   如果差很多，先怀疑算子实现差异（极少数情况）或预处理不一致（绝大多数）。

10. **性能不达标**
    先量化（fp32 → int8 通常快 2~3 倍），再考虑算子裁剪
    （`--include_ops_by_config` 只编模型用到的算子，体积能小一半）。

---

## 8. 优化路线（按性价比排序）

| 手段 | 收益 | 成本 | 备注 |
|---|---|---|---|
| Int8 量化（QDQ） | x86 实测 1.36~2.03×（小模型反而 0.61×）；**ARMv7 无 int8 点积，收益待上板** | 低 | 需要**真实**校准集；见 [12-量化实测](12-量化实测.md) |
| 算子裁剪（minimal build） | 体积减半 | 低 | 换模型要重编 |
| 减小输入分辨率 | 平方级收益 | 低 | 最有效，但影响精度 |
| 多线程（intra_op） | 1.6× (双核) | 低 | Cortex-A9 只有 2 核 |
| 模型结构（MobileNet 系列） | 数量级 | 中 | 从训练侧解决 |
| NEON 手写 kernel | 1.2~1.5× | 高 | ORT 已经用了 NEON |
