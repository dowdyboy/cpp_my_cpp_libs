# 协议编解码与崩溃捕获（my::codec / my::crash）

这两块都是"每个嵌入式工程都会各写一遍、写错了又很难查"的小工具，所以收进 `core`：

- **`my::codec`**：CRC16/CRC32、hex、base64、COBS —— 串口/网口自定义帧的底座；
- **`my::crash`**：进程被信号/未处理异常带走时，往 stderr 留一段可贴进 issue 的现场。

> `TcpServer` 不在这里，见 [网络与 HTTP §9](10-网络与HTTP.md)。

---

## 1. `my::codec`

header-only（`#include <my_cpp_libs/core/codec.hpp>`），不依赖任何三方库，不抛异常。

### 1.1 CRC

| 函数 | 参数（poly/init/refin/refout/xorout） | `"123456789"` 的 check |
|---|---|---|
| `crc16_ccitt(data, n, init=0xFFFF)` | 0x1021 / 0xFFFF / false / false / 0 | **0x29B1**（CCITT-FALSE） |
| `crc16_modbus(data, n, init=0xFFFF)` | 0x8005（表用反射 0xA001）/ 0xFFFF / true / true / 0 | **0x4B37**（MODBUS） |
| `crc32_ieee(data, n)` | 0x04C11DB7（表 0xEDB88320）/ 0xFFFFFFFF / true / true / 0xFFFFFFFF | **0xCBF43926**（ISO-HDLC / zlib / 以太网） |

一次性函数之外还有增量类（串口/网口按块喂）：

```cpp
my::codec::Crc32 crc;
while (auto block = next_block()) crc.update(block.data(), block.size());
const std::uint32_t fcs = crc.value();   // value() 才做 xorout
```

`Crc16Ccitt` / `Crc16Modbus` 同样可用（构造时给 init）。

> 头注释里写了每个变体的完整参数。**不要**只写 "CRC16"——CCITT、MODBUS、XMODEM、
> ARC 的 check 值完全不同，这是串口调试里最常见的"两边都算 CRC16 但对不上"。

### 1.2 hex / base64

```cpp
const std::string h = my::codec::hex_encode(data, n);            // 小写
const std::string H = my::codec::hex_encode(data, n, /*upper=*/true);

std::vector<std::uint8_t> raw;
auto st = my::codec::hex_decode("0aFF", raw);                    // 大小写都收

const std::string b64  = my::codec::base64_encode(data, n);       // RFC 4648 标准字母表
const std::string b64u = my::codec::base64_encode(data, n, /*url_safe=*/true,
                                                  /*padding=*/false);
auto st2 = my::codec::base64_decode(b64u, raw);                   // 双字母表/忽略空白/可缺 padding
```

失败（奇数长度、非法字符、非法 padding）返回 `ParseError`，**`out` 保持不变**；
成功时 `out` 被整体替换。

### 1.3 COBS（Consistent Overhead Byte Stuffing）

串口/字节流里最省事的"分帧"方式：编码后帧里**不会出现 0x00**，接收端用 0x00 当分隔符。

```cpp
// 发送：payload -> COBS 帧（含末尾 0x00）
auto frame = my::codec::cobs_encode(payload.data(), payload.size());
serial.write_all(frame.data(), frame.size(), 200ms);

// 接收：按 0x00 切出帧 -> 解码
std::vector<std::uint8_t> payload;
auto st = my::codec::cobs_decode(frame.data(), frame.size(), payload);
```

- 编码结果**含末尾 0x00 分隔符**；解码时带不带分隔符都接受。
- `cobs_max_encoded_size(n) = n + n/254 + 2`（**含**分隔符，可直接拿来分配缓冲）。
- 板端零分配：`cobs_encode_into(src, n, dst, cap)` / `cobs_decode_into(...)` 返回实际写入
  字节数；`cap` 不足返回 `OutOfRange` 且不写 `dst`。

### 1.4 一个完整的串口帧格式

```text
COBS( CRC16 + payload ) | 0x00
     ^^^^^^ 2 字节小端 CRC16/CCITT，覆盖 payload（COBS 输出本身以 0x00 结尾）
```

伪代码：

```cpp
std::vector<std::uint8_t> body;
const std::uint16_t crc = my::codec::crc16_ccitt(payload.data(), payload.size());
body = {std::uint8_t(crc & 0xFF), std::uint8_t(crc >> 8)};
body.insert(body.end(), payload.begin(), payload.end());
auto frame = my::codec::cobs_encode(body.data(), body.size());
```

接收端先按 0x00 切帧 → `cobs_decode` → 校验前 2 字节 CRC → 把 payload 交给业务。
COBS + CRC 的组合能同时解决"粘包/半包"和"坏帧"，比 4 字节长度前缀更适合
**噪声信道/无长度字段的旧协议**。

### 1.5 测试

`tests/test_codec.cpp`（套件 `codec`）用标准向量钉住：CRC 的三个 check 值、
增量 vs 一次性、RFC 4648 base64 向量、COBS 规范里的两个经典向量、全 256 字节往返、
254/255 长块边界、`*_into` 与 vector 版逐字节一致、非法帧/非法字符返回错误。

## 2. `my::crash`

### 2.1 用法

```cpp
#include <my_cpp_libs/core/crash.hpp>

int main() {
    my::crash::install();          // 进程启动早期调用一次
    // ... 业务 ...
    return 0;
}
```

可选配置：

```cpp
my::crash::Options opt;
opt.install_signal_handlers = true;   // POSIX 5 个信号；Windows SIGABRT + SEH
opt.install_terminate_handler = true; // std::set_terminate
opt.write_build_info = true;          // 崩溃头带 BuildInfo（版本/commit/平台）
opt.print_backtrace = true;
opt.max_frames = 32;                  // 夹到 [1,128]
my::crash::install(opt);
```

### 2.2 崩溃时看到什么

```text
my_cpp_libs crash: my_cpp_libs 0.1.9 | AMD64-Windows | GNU 15.2.0 | Release | @4d4a444 | ptr=64
  exe      : D:\proj\app.exe      pid : 12345
  capture  : max_frames=32 backtrace=on
  signal   : SIGSEGV (11)  t+12.345s after install
  backtrace: captured 8 frame(s), max=32
    #000 0x00007ff65f40218d
    #001 0x00007ff65f401234
  note     : best-effort capture; this handler does NOT produce a core dump.
```

板端现场把这段连同 `BuildInfo::summary()` 贴回来，至少能回答"哪次构建、哪个信号、
大致哪条调用链"。

### 2.3 能力边界（重要）

- **best-effort**：处理器运行在异步信号上下文，只做 `write(2)`/`WriteFile` + 栈回溯。
  `printf`/`iostream`/`malloc`/`std::string` 都可能死锁，所以 install() 阶段把
  构建信息/进程信息预格式化进静态定长缓冲。
- **不替代 core dump**：处理器写完 `_Exit(3)`，故意不 re-raise，因此不产生 core 文件。
  生产环境请同时开：
  - Linux：`ulimit -c unlimited` + `coredumpctl`；
  - Windows：WER LocalDumps，或 `procdump -ma -e`。
- **地址→符号**必须用同一份构建的符号：
  - Linux 加 `-rdynamic` 可直接看到函数名；否则 `addr2line -f -C -e app 0x...`；
  - Windows SEH 路径只输出地址（`SymFromAddr` 在崩溃上下文会拿装载器锁/分配堆内存），
    用 PDB + `llvm-symbolizer`/`dumpbin` 离线解析。
- POSIX 装了 `sigaltstack`，栈溢出（SIGSEGV）也能运行处理器；Windows 交回旧过滤器，
  **WER dump 仍然会产出**。
- 没调用 `install()` 时本模块完全不介入；`uninstall()` 会恢复安装前的处理器，
  便于测试/嵌入到别的框架。

### 2.4 测试

`tests/test_crash.cpp`（套件 `crash`）：

- `crash_backtrace_text_is_usable`：非信号上下文的 `backtrace_text()` 能拿到帧；
- `crash_install_uninstall_is_idempotent`：重复 install/uninstall 不崩、之后仍可用。

真正的崩溃路径由子进程探针验证（仓库外）：`raise(SIGABRT)` 后 stderr 必须出现
`my_cpp_libs crash:` 头和帧行；Windows 另验 SEH `0xC0000005`、Linux 另验栈溢出。
