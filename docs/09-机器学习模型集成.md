# 机器学习模型集成（sklearn → ONNX → 板端）

> 结论：**可行，而且不需要给 C++ 侧引入任何新的三方库**。
> sklearn 模型用 skl2onnx 导出成 ONNX，走板端已有的 ONNX Runtime 后端；
> `my::ml` 只做"表格模型"这一层薄封装（双输出、特征顺序、类别名）。
>
> 本文记录导出链路、API、数值一致性怎么保证、以及踩过的坑。

---

## 1. 整条链路

```
Python（训练机，conda t2xpu）
  sklearn 训练 ──pickle──> tools/sklearn_export.py ──skl2onnx──> model.onnx
                                                              └> model.json（sidecar）
板端（armv7）
  model.onnx + model.json ──my::ml（内部走 my::infer + ORT 1.18.1）──> Prediction
```

为什么不用别的路：

| 方案 | 结论 |
|---|---|
| **ONNX + ORT**（本方案） | ✅ 已支持、覆盖广（14 种 estimator 实测全部可导）、精度对得上 |
| 手写 C++ 推理（导出系数 JSON） | ⏸ 线性模型可行（430 字节、20 行代码），树集成要自己实现遍历；留作"没有 ORT 时的逃生路线" |
| 代码生成（m2cgen / emlearn） | ⏸ 零运行时，但覆盖面不如 ONNX；真要做再引 |
| treelite / tl2cgen | ❌ 自带运行时 + 构建依赖，armv7 交叉编译和 MSVC 都麻烦，收益不划算 |
| 把 sklearn 放进 C++（libsvm、mlpack、dlib） | ❌ 和 ORT 能力重复，体积/构建成本高 |

## 2. 导出：`tools/sklearn_export.py`

```bash
conda activate t2xpu
python tools/sklearn_export.py --model clf.pkl --out models/ml/iris_logreg.onnx
```

产出两个文件：

- `model.onnx` —— opset **固定 18**（板端 ORT 1.18.1 的保守上限），分类器的
  `zipmap=False`（否则输出是 `seq<map>`，C++ 侧没法人吃）；
- `model.json` —— sidecar 元数据：

```json
{
  "format": "my_cpp_libs.ml/1",
  "kind": "classifier",
  "model":   { "onnx": "iris_logreg.onnx", "sha256": "71F8…", "opset": {"ai.onnx": 18, "ai.onnx.ml": 1} },
  "input":   { "name": "input", "dtype": "float32", "n_features": 4,
               "features": ["sepal_length", "sepal_width", "petal_length", "petal_width"] },
  "output":  { "items": [{"name": "label", "dtype": "int64"}, {"name": "probabilities", "dtype": "float"}],
               "n_classes": 3, "classes": ["setosa", "versicolor", "virginica"], "class_ids": [0,1,2] },
  "preprocess": { "type": "none", "embedded_in_onnx": false },
  "training":   { "sklearn": "1.9.1", "onnx": "1.20.1", "python": "3.13.11" },
  "check":      { "max_abs_prob_diff": 1.5e-07, "argmax_agreement": 1.0 }
}
```

导出时会**自动对拍**：同一批随机输入，比较 sklearn 的 `predict_proba` 和
ONNX Runtime 的输出，`max_abs_prob_diff` 写进 sidecar。超过 1e-3 会告警。

> sidecar 里为什么要存特征名？因为模型只认 float 数组，**特征顺序错一位不会报错**，
> 只会输出垃圾。`my::ml` 运行时拿它校验维度、业务代码拿它对齐特征。

## 3. C++ 侧：`my::ml`

```cpp
#include <my_cpp_libs/ml/ml.hpp>

auto model = my::ml::Model::load("models/ml/iris_logreg.onnx");   // 自动找同名 .json
if (!model) { my::log::error("{}", model.status().to_string()); return; }

const auto& m = model.value().meta();
my::log::info("特征顺序: {}", ...);      // ["sepal_length", ...]
my::log::info("类别: {}", ...);          // ["setosa", ...]

// 单样本
auto p = model.value().predict_one({5.1f, 3.5f, 1.4f, 0.2f});
// p.label = 0, p.label_name = "setosa", p.scores = {0.9816, 0.0184, 0.0000}

// 批量：特征按行拼起来，一次 run
std::vector<float> batch = { /* 样本1的4个特征, 样本2的4个特征, ... */ };
auto preds = model.value().predict(batch);
```

`my::ml` 解决了三个具体问题（这也是不直接裸用 `my::infer` 的原因）：

1. **双输出**：sklearn 分类器是 `label(int64) + probabilities(float32)` 两个输出，
   `infer::run_single_f32()` 只支持 1 进 1 出；
2. **特征校验**：`predict()` 会检查 `features.size() % n_features == 0`，
   错了直接 `InvalidArgument`，不会静默算出一堆垃圾；
3. **类别名**：`label → "setosa"` 由 sidecar 驱动，不需要业务代码写死映射表。

约定与限制：

- 分类器输出列数必须等于类别数，否则报 `RuntimeError`（模型和 sidecar 不匹配）；
- `Model` **不可拷贝**、**不可多线程并发**（和 `infer::Session` 同一个契约）；
- 没有 ONNX Runtime 的构建（MinGW / 精简板端）上，`load()` 会返回 `Unsupported`，
  单元测试自动跳过 —— 这是 infer 组件既有的降级语义。

## 4. 数值一致性怎么保证

`models/ml/` 下的三个演示模型由 `tools/train_ml_models.py` 生成，**都进 git**（总共约 25 KB）：

| 模型 | 用途 | ONNX | 参数 |
|---|---|---|---|
| `iris_logreg` | 线性分类（4 特征 3 类） | 534 B | LogisticRegression |
| `gbdt_20f` | 树集成（20 特征 2 类） | 17 KB | GradientBoosting, 30 棵 |
| `ridge_10f` | 回归（10 特征） | 304 B | Ridge |

每个模型旁边有 `.golden.tsv`：8 行固定输入 + **sklearn 自己算出来的**输出。
`tests/test_ml.cpp` 用 C++ 读这个文件做对拍：

```
sklearn 训练 → ONNX → my::ml(ORT) ⟶ 与 golden 比，概率误差 < 2e-4
```

这样换 sklearn / skl2onnx 版本时，只要重新跑 `train_ml_models.py` 就能发现漂移，
而不是等板端上线后才发现"结果不对但没人报错"。

## 5. 覆盖面（实测，sklearn 1.9.1 / skl2onnx 1.20.0）

| 模型 | 导出 | 大小 | opset | 备注 |
|---|---|---|---|---|
| LogisticRegression / Ridge | ✅ | 0.3~0.5 KB | 18 | LinearClassifier/Regressor |
| DecisionTree / RandomForest / ExtraTrees | ✅ | 1~7 KB | 18 | TreeEnsemble |
| AdaBoost / HistGradientBoosting | ✅ | 10~11 KB | 16/18 | HistGBDT 也能导 |
| SVC（rbf） | ✅ | 2.3 KB | 9 | SVMClassifier |
| KNN / MLP | ✅ | 1~5 KB | 18/16 | |
| PolynomialFeatures / StandardScaler + 模型 | ✅ | 0.6~3 KB | 18 | 预处理烘进图里 |
| ColumnTransformer（数值+OneHot） | ✅ | 1.1 KB | 13 | 表格数据常见形态 |
| RandomForest 500 棵 / depth 12 | ✅ | **303 KB** | 18 | 大一点的森林也就这个量级 |

**导出失败时的态度**：skl2onnx 报错就说明这个模型不能走 ONNX，不要硬转 ——
换模型结构，或者退回"导出参数 + 自己实现"。

板端兼容性：模型 opset ≤ 18、`ai.onnx.ml` = 1、算子都是 ORT 长期支持的
（`TreeEnsemble*` 从 ORT 1.0 就有）。**已在板端实跑**：板端 ORT 1.18.1 加载 3 个 opset-18 模型，9 个 golden 对拍用例全过，单次推理 0.07~0.10 ms。

## 6. 体积与性能

| 项 | 量级 |
|---|---|
| 模型文件 | 0.3 KB（线性）~ 300 KB（500 棵树） |
| ORT 运行时 | 已有，约 11 MB（`libonnxruntime.so`） |
| 单次推理（x64，Python ORT，含调用开销） | 0.3~0.9 ms |
| 板端实测（A9 @666MHz） | 单次 0.093~0.095 ms（2026-11-16 上板实测，见 [06 §0](06-板端验证手册.md)） |

所以选型建议：

- **每帧一次 / 几十个特征**的判别、打分、分类：ONNX 路完全够；
- **1 kHz 以上**或不想带 ORT：把线性模型导出成系数 JSON，C++ 手写 20 行
  （`y = Wx + b` + softmax），精度和 ONNX 一致（实测 1.7e-7）；
  树集成的原生实现留作后续（JSON 里存 nodes/children/values，遍历约 60 行）。

## 7. 板端实测（2026-11-16）与后续

**已验证**（Zynq-7020，ORT 1.18.1，glibc 2.30）：

| 项 | 结果 |
|---|---|
| 模型加载 | 3 个 opset-18 模型全部加载成功（`ai.onnx.ml` = 1） |
| 数值一致性 | 与 sklearn golden 对拍误差 < 2e-4，分类结果完全一致 |
| 单次推理延迟（Zynq A9） | iris_logreg **0.093~0.095 ms**、gbdt_20f **0.088~0.096 ms**、ridge_10f **0.066 ms**（200 次均值） |
| 单次推理延迟（Pi 4B） | iris **0.017~0.018 ms**、gbdt **0.016 ms**（ORT 1.19.2，200 次均值） |
| 部署体积 | 3 个模型合计 25 KB + sidecar；ORT .so 10.9 MB（与推理共用） |

> **注意 ORT 版本**：≥1.20 的 aarch64 官方包按 ARMv8.2 编译，在 Cortex-A72（Pi 4）上会 `SIGILL`，
> 要用 1.18.1 / 1.19.2 或自己按 `-march=armv8-a` 编。
>
> 0.1 ms 意味着"每帧一次判别"完全不是瓶颈，甚至 1 kHz 级别也够；
> 之前担心的"板上要不要为表格模型单独写原生推理"，现在看**没必要**。

**还没做**：

- **原生小模型路径**（线性模型导出系数 JSON、20 行 C++）：现在看收益很小，除非要给没有 ORT 的板子留后路；
- **XGBoost / LightGBM**：需要另装 `onnxmltools` 导出，导出后同样用 `my::ml` 加载；
- ~~**模型文件校验**~~ ✅ 0.1.7 已做：sidecar 里的 `sha256` 由 `my::hash::sha256_file_hex()` 核对，`Model::load()` 默认开启（`verify_hash=false` 可关）。
  守的是"换了模型但忘了更新 sidecar"：以前的表现是推理结果莫名其妙，现在是一个明确的加载错误。

## 8. 复现

```bash
# 1) 训练 + 导出（只需一次，产物已进 git）
conda activate t2xpu
python tools/train_ml_models.py

# 2) 跑 C++ 侧对拍（需要 ORT 后端）
cmake --preset win-msvc && cmake --build --preset win-msvc
ctest --preset win-msvc -R ml_ --output-on-failure

# 3) 演示
build\win-msvc\bin\Release\example_ml.exe models\ml\iris_logreg.onnx
```
