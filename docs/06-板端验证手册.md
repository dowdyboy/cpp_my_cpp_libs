# 板端验证手册

> 板子到手后照着做，30 分钟内能拿到"这块板子能不能跑、跑多快"的结论。
> 目标不是"能跑就行"，而是**拿到真实延迟数字，据此决定板端主力后端**。

### 0.3 历史性能数据（上一轮，ncnn 已开）

| 项目 | 结果 |
|---|---|
| small_cnn（32×32，≈2 MMAC） | **2.47 ms**（ncnn） |
| bench_cnn（224×224，≈300 MMAC） | **585 ms**（ncnn） / **865 ms**（ORT） |
| MobileNetV2-12（官方预训练） | **1367 ms**（ORT；ncnn 转不了） |
| 内存峰值 | 140~153 MB |
| 1 线程 vs 2 线程 | 549.8 vs 549.0 ms（**基本无差别**） |
| ORT 动态库体积 | 10.9 MB（strip） |

**换算**：300 MMAC / 0.585 s ≈ **513 MMAC/s ≈ 1.0 GFLOPS**，和 A9 NEON 峰值估算
（0.5~1.5 GFLOPS）对得上。

> **多线程没有收益**：Cortex-A9 双核共享 L2 和 DDR 带宽，卷积是访存瓶颈。
> 部署时用单线程，另一个核留给采集/通信。

### 0.4 后端选择（有数据了）

同一个模型 `bench_cnn` 在两个后端上的表现：

| 后端 | 延迟 | 备注 |
|---|---|---|
| ncnn | **585 ms** | 快 1.48×，体积小 |
| ONNX Runtime | 865 ms | 慢一些，但什么模型都能吃 |

**结论**：

1. 模型能干净地转成 ncnn → **用 ncnn**（快一半，体积小得多）；
2. 转不了（官方预训练模型、带动态 reshape 的）→ **用 ORT**，代价是 1.4 s/次；
3. 两者可以编进同一个二进制，运行时按模型扩展名自动选。

**表格模型例外**：sklearn 这类小模型走 ORT 只有 **≈0.07~0.10 ms**，
完全不需要 ncnn（体积换不来收益）。

### 0.7 aarch64：Raspberry Pi 4B（Debian 13）

**环境**

```
SOC        Raspberry Pi 4 Model B Rev 1.5（Cortex-A72 ×4，无 FP16 算术）
系统       Debian 13 (trixie)，内核 6.12.75+rpt-rpi-v8
glibc      2.41     libstdc++ 6.0.33 (GCC 14.2)
内存/磁盘  3.8 GB / 28 GB
工具链     ARM GNU Toolchain 14.2.Rel1（aarch64-none-linux-gnu，sysroot glibc 2.40）
```

**结果（2026-11-16）**

| 项 | 结果 |
|---|---|
| 单元测试 | **158 / 158 通过，1 秒**（含 ml 9、cv 8） |
| ml 表格模型 | iris_logreg **0.017 ms/次**、gbdt_20f **0.016 ms**（ORT 1.19.2） |
| bench_cnn（224×224） | **74.3 ms**（Zynq-7020 是 775 ms，**快 10.4×**） |
| example_ml / opencv / pipeline / signal | 57 ms / 64 ms / 10 ms / 12 ms |

**两个必须知道的坑**

1. **ORT ≥ 1.20 的 aarch64 包在 Cortex-A72 上 `SIGILL`**（非法指令）。
   实测官方 1.21.0 和 Debian 的 `libonnxruntime1.21` 都是如此：只 `dlopen` 就在静态初始化里执行
   `fmov v1.4h`（ARMv8.2 FP16 指令），而 A72 是 ARMv8.0。
   **对策：用 ORT 1.18.1 / 1.19.2**（实测两者都能加载），或者自己按 `-march=armv8-a` 从源码编。
2. **交叉编 OpenCV 的共享库时不能带 `-no-pie`**：链接器会去找可执行入口，
   报 `crt1.o ... undefined reference to 'main'`。`-no-pie` 只能给可执行文件
   （`cmake/toolchains/linux-aarch64.cmake` 已修正）；另外交叉编 OpenCV 要加
   `-DCMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY`，否则探测链接也会撞同一个错。

**部署内容**：`bin/`（9 个可执行）+ `models/` + `lib/`（自编 OpenCV 4.12 的 3 个 .so、
ORT 1.19.2 的 `libonnxruntime.so.1`），`run.sh` 里设 `LD_LIBRARY_PATH`。

**打包命令**（同一份脚本，MSYS bash 里跑；它按 `readelf -d` 的 NEEDED 自动收 `.so`）：

```bash
PATH=/d/ProgramData/arm-gnu-toolchain-14.2.rel1-mingw-w64-x86_64-aarch64-none-linux-gnu/bin:$PATH \
  bash scripts/deploy-armv7.sh build/verify-aarch64 dist/board_deploy-aarch64.tar.gz
```

上板：

```bash
scp dist/board_deploy-aarch64.tar.gz root@192.168.0.150:/root/
ssh root@192.168.0.150 'cd /root && tar xzf board_deploy-aarch64.tar.gz && cd board_deploy && ./verify.sh'
```

### 0.5 一个必须知道的前提：glibc 版本

这块板子是 **PetaLinux 2020.2**：glibc **2.30**、libstdc++ **6.0.27**。
PC 上默认那份 SDK 是 2024 版（glibc 2.39），编出来的动态链接产物在板上直接报
`GLIBC_2.38 not found`。

**正解：用板子配套的 PetaLinux 2020.2 SDK。**

SDK 在 VMware 虚拟机上（Ubuntu 18.04，192.168.159.135）：
`/home/lfbhlx/Projects/adda_fft/linux/sdk`

```bash
source <sdk>/environment-setup-cortexa9t2hf-neon-xilinx-linux-gnueabi
# 之后 arm-xilinx-linux-gnueabi-g++ (GCC 9.2.0) 就在 PATH 里
```

本项目已经带了对应的工具链文件：

```cmake
# cmake/toolchains/petalinux-2020.2-zynq.cmake
cmake -S . -B build/sdk -G Ninja \
      -DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/petalinux-2020.2-zynq.cmake \
      -DCMAKE_BUILD_TYPE=Release
```

工具链文件里的 `MYLIB_PETALINUX_SDK` 可以覆盖，也不强制要求先 source
（会自动去 SDK 的 `x86_64-petalinux-linux/usr/bin` 下找编译器）。

#### 三种方案对比

| 方案 | 产物 | 适用 |
|---|---|---|
| **A. 用匹配的 SDK（推荐）** | 动态链接，2.5 MB | 长期方案，ORT/ncnn 都能用 |
| B. 全静态链接 | 5.4 MB，自带 libc | 没有匹配 SDK 时的应急 |
| C. 升级板子镜像 | — | 有工程成本 |

  手动部署验证：静态版 158/158 通过，SDK 动态版也 158/158 通过；
延迟在 2.5~2.6 ms（small_cnn）/ 550~585 ms（bench_cnn）之间，差异是测量波动。

#### 交叉编译 ONNX Runtime 的版本约束

**ORT 1.18.1 是最后一个支持 GCC 9 的版本**（1.19+ 要求 GCC ≥ 11）。
板子的 SDK 是 GCC 9.2，所以：

| 目标 | 能用的 ORT |
|---|---|
| PetaLinux 2020.2（GCC 9.2） | **≤ 1.18.1** |
| PetaLinux 2024（GCC 13.3） | ≤ 1.23.2 |

另外 ORT 1.18 的 CMake 会去下载 Eigen，而虚拟机上 CMake 的 `file(DOWNLOAD)` 走代理不稳，
所以要用预置的 Eigen（`-Donnxruntime_USE_PREINSTALLED_EIGEN=ON -Deigen_SOURCE_PATH=...`）。

## 1. 部署前先确认三件事

在板子上执行：

```bash
# ① glibc 版本：必须 >= 产物要求的版本（取决于你用哪个 armv7 预设，见下表）
ldd --version | head -1

# ② libstdc++ 版本
strings /usr/lib/libstdc++.so.6 2>/dev/null | grep GLIBCXX_3.4.3 | tail -1

# ③ CPU 是否有 NEON（Cortex-A9 必须有）
grep -E 'model name|Features' /proc/cpuinfo | head -2
```

**先看这张表对上号**（本项目这个板子的实测值是 glibc 2.30 / GLIBCXX 3.4.27）：

| 你用的预设 | 产物要求 | 这块板（2.30）能跑吗 |
|---|---|---|
| `linux-armv7`（2024 SDK） | glibc ≥ 2.38 / GLIBCXX 3.4.30 | ❌ 只能做编译验证 |
| `linux-armv7-static` | 无（自带 libc） | ✅ |
| `linux-armv7-sdk2020`（配套 SDK） | glibc ≥ 2.30 | ✅ |

| 检查项 | 预期 | 不满足怎么办 |
|---|---|---|
| glibc | ≥ 产物要求的版本（上表） | 换 `-static` 或换配套 SDK 重编，而不是去改板子 |
| GLIBCXX | ≥ 3.4.30（动态版） | 同上，或加 `-static-libstdc++ -static-libgcc` |
| NEON | Features 含 `neon` | 没有 NEON 的话 ONNX Runtime 跑不起来（编译时就假定了 NEON） |

> 这三个数字对不上时**不要试图在板子上装库**，正确做法是在编译侧换 sysroot / 换静态。
> 板子的 rootfs 通常没有包管理器，折腾起来比重新编一遍还慢。

## 2. 一键部署

### 2.1 静态产物（glibc 不匹配时用这个）

```powershell
cmake --preset linux-armv7-static
cmake --build --preset linux-armv7-static
```

（等价于 `-DCMAKE_TOOLCHAIN_FILE=cmake/toolchains/linux-armv7-zynq.cmake
-DMYLIB_ENABLE_ONNXRUNTIME=OFF -DMYLIB_ENABLE_NCNN=ON
-DMYLIB_BUILD_EXAMPLES=OFF -DCMAKE_EXE_LINKER_FLAGS=-static`）

产物自带 libc/libstdc++/ncnn，**不依赖板子的任何库**，也不用设 `LD_LIBRARY_PATH`。

> 注意：静态版没有 ORT（它的 `.so` 没法静态化），所以只能用 ncnn。
> 需要 ORT 的模型请走 2.3 的配套 SDK 动态链接路线。

### 2.2 部署（密码认证，走 WSL）

```powershell
wsl -d Ubuntu-24.04 -u root -- bash scripts/board-deploy-wsl.sh
```

脚本会：推送 → 跑单元测试 → 跑 small_cnn / bench_cnn 基准 → 报内存峰值。

可用环境变量覆盖：

| 变量 | 默认 | 说明 |
|---|---|---|
| `BOARD` | `192.168.0.130` | 板子 IP |
| `BOARD_PASS` | `root` | 密码 |
| `DEST` | `/tmp/mylib` | 远端目录 |

> 为什么走 WSL：Windows 没有 `sshpass`，密码认证在非交互脚本里过不去。
> 配好 ssh 密钥后，也可以用 `scripts/deploy-and-bench.ps1`。

### 2.3 动态链接产物（板子配套 SDK，推荐给要用 ORT 的场合）

```powershell
# 在装了 PetaLinux 2020.2 SDK 的 Linux 上（比如那台 VMware 虚拟机）
cmake --preset linux-armv7-sdk2020
cmake --build --preset linux-armv7-sdk2020
```

产物的 glibc 要求是 2.30，正好匹配这块板；部署时带上 `libonnxruntime.so.1.18.1`。

> **不要用 `linux-armv7`**：那是 2024 版 SDK（glibc 2.39），上板直接
> `GLIBC_2.38 not found`。这条以前只写在 B 方案里，容易误用，现在预设名和描述已经区分开了。

### 2.4 板子还没到手？先生成离线包


### 2.5 用 `scripts/deploy-armv7.sh` 一键打包（推荐，Linux 构建机上跑）

板端部署包里需要的东西是"可执行 + 非系统动态库 + models + 启动器"，手工拼容易漏 `.so`。
仓库里带了一个脚本，按 `readelf -d` 的 NEEDED 自动收集：

```bash
# 在 Linux 构建机上（VM），先 source 板子配套的 SDK
source <sdk>/environment-setup-cortexa9t2hf-neon-xilinx-linux-gnueabi
cd cpp_my_cpp_libs
bash scripts/deploy-armv7.sh            # -> dist/board_deploy-armv7.tar.gz（约 25 MB）
```

脚本做的事：

1. 9 个可执行文件 `strip --strip-unneeded`（`mylib_tests` 从 30 MB 降到 **1.42 MB**）；
2. 扫每个二进制的 `NEEDED`，把**非系统库**（ORT / OpenCV）从 `third_party/` 里找出来拷进 `lib/`；
3. 带上 `models/`（含 `ml/*.golden.tsv`）；
4. 生成 `run.sh`（设 `LD_LIBRARY_PATH` + `MYLIB_TEST_MODELS_DIR`）和 `verify.sh`（一键回归）。

上板：

```bash
scp dist/board_deploy-armv7.tar.gz root@192.168.0.130:/home/root/
ssh root@192.168.0.130 'cd /home/root && tar xzf board_deploy-armv7.tar.gz'
ssh root@192.168.0.130 'cd /home/root/board_deploy && ./verify.sh'
```

> 注意：测试里的模型目录优先读环境变量 `MYLIB_TEST_MODELS_DIR`，
> 不设时会退回到编译期路径（另一台机器的路径），所以**一定要用 `run.sh` 起**
> 或者自己 `export MYLIB_TEST_MODELS_DIR=/home/root/board_deploy/models`。

## 3. 手动部署（不想用脚本）

```bash
# 电脑侧（必须先有配套 SDK：linux-armv7 预设的 glibc 2.39 产物上不了 2.30 的板子）
scp build/linux-armv7-sdk2020/bin/{mylib_tests,model_inspect,example_pipeline} root@<ip>:/tmp/mylib/
scp third_party/onnxruntime-armv7-petalinux2020/lib/libonnxruntime.so.1.18.1 root@<ip>:/tmp/mylib/
scp models/small_cnn.onnx root@<ip>:/tmp/mylib/models/

# 用了 OpenCV（-DMYLIB_ENABLE_CV=ON）的话，三个 .so 也要一起拷：
#   third_party/opencv-4.12.0-armv7/lib/libopencv_{core,imgproc,imgcodecs}.so.412
scp third_party/opencv-4.12.0-armv7/lib/libopencv_*.so.412 root@<ip>:/tmp/mylib/

# 板侧
cd /tmp/mylib
chmod +x mylib_tests model_inspect example_pipeline
export LD_LIBRARY_PATH=$PWD:$LD_LIBRARY_PATH
export MYLIB_TEST_MODELS_DIR=$PWD/models
```

> **SONAME 不能改**：板端 ORT 1.18.1 的 SONAME 是 `libonnxruntime.so.1.18.1`
> （不是 `.so.1`）；OpenCV 4.12 的是 `libopencv_core.so.412` 等。可执行文件里记录的
> 就是这些名字，改名会报 `error while loading shared libraries`。
> 实测 armv7 产物（`-DMYLIB_ENABLE_CV=ON -DMYLIB_ENABLE_NCNN=ON`）的 `NEEDED` 是：
>
> ```
> libonnxruntime.so.1.18.1  libopencv_core.so.412  libopencv_imgproc.so.412
> libopencv_imgcodecs.so.412  libpthread.so.0  libstdc++.so.6  libm.so.6
> libgcc_s.so.1  libc.so.6  ld-linux-armhf.so.3
> ```
>
> 另外：SDK 环境会带 `-g`，编出来的可执行文件很大（`mylib_tests` 78 MB），
> 拷之前先 `arm-xilinx-linux-gnueabi-strip --strip-unneeded`，能降到几 MB。

## 4. 必跑的四项

```bash
# ① 单元测试：全绿才算环境没问题
```

## 5. 常见错误对照表

| 报错 | 原因 | 解决 |
|---|---|---|
| `GLIBC_2.xx not found` | 板子 glibc 比编译用的旧 | 用板子 sysroot 重编 |
| `GLIBCXX_3.4.xx not found` | libstdc++ 版本不够 | 重编，或 `-static-libstdc++` 静态链接 |
| `libonnxruntime.so.1: cannot open` | 没设 `LD_LIBRARY_PATH` 或改了文件名 | 放到同目录并 `export LD_LIBRARY_PATH=$PWD` |
| `Illegal instruction` | 目标板和编译参数不匹配（如用了 `-mcpu=cortex-a9` 但板子是 A7） | 改 toolchain 的 `-mcpu` |
| `Bus error` / SIGBUS | 内存对齐问题（Eigen 定长类型） | 用 `my::math::AlignedVector`，或 `-DEIGEN_MAX_ALIGN_BYTES=16` |
| 推理结果与 x86 差异大 | 预处理参数不一致 | 核对 `scale/mean/stddev/颜色顺序/布局` 五项 |
| `mmap` 失败 / 被 OOM kill | 模型太大，内存不够 | 换小模型或量化 |

## 6. 后端选择：ORT 还是 ncnn

两个后端**在板上都能跑**（都用配套 SDK 编译，动态链接）：

| 指标 | ONNX Runtime | ncnn |
|---|---|---|
| 版本 | 1.18.1（GCC 9 的上限） | 20250503 |
| 体积 | `libonnxruntime.so` **10.9 MB** | 静态库，编进程序约 +2 MB |
| 算子覆盖 | ★★★★★ 什么模型都吃 | ★★★☆☆ 需要转换，转不了就没辙 |
| bench_cnn（同一模型） | 865 ms | **585 ms** |
| MobileNetV2（官方模型） | **1367 ms** ✅ | ❌ 转换失败 |
| 运行依赖 | glibc 2.29 / GLIBCXX 3.4.26 | 无（静态） |

**结论**：

1. 模型能干净地转成 ncnn → **用 ncnn**（快 1.48×，体积小）；
2. 转不了（官方预训练、带动态 reshape）→ **用 ORT**，代价是 1.4 s/次；
3. 两者可以编进同一个二进制，运行时按扩展名自动选（`.param` → ncnn，`.onnx` → ORT）。

### 为什么 ncnn 更快

同一个模型，ncnn 585 ms vs ORT 865 ms。可能的原因：

- ORT 1.18 的 ARM CPU kernel 比 ncnn 的晚几年优化；
- ncnn 默认对 3×3 卷积做了更适合 Cortex-A9 的汇编；
- ORT 的算子调度/内存分配开销更大（它的强项是算子覆盖面，不是单点速度）。

> 如果模型必须用 ORT，又嫌慢，可以试 `--threads 2`（本项目实测**没有收益**，
> A9 双核共享带宽，卷积是访存瓶颈）。

## 7. 板上还可以顺手验的

```bash
# 多线程能提速多少（Cortex-A9 双核，理论上限 2x）
./model_inspect models/small_cnn.onnx --bench 50

# 浮点能力粗测（估算算力上限）
cat /proc/cpuinfo | grep BogoMIPS

# 温度（长时间推理会不会降频）
cat /sys/class/thermal/thermal_zone0/temp 2>/dev/null
```

如果长时间推理后延迟明显上升，说明散热受限在降频——这在实际部署里比"峰值性能"更重要。
