# 图像链路（stb）与无异常构建

> 本文记录两件事的**结论与依据**：
> 1. 板端（无 OpenCV）的图像链路怎么走 —— 新增的 `my::image` 组件；
> 2. `-fno-exceptions` 这条承诺被收窄到了哪里，以及为什么不能收得更宽。

---

## 1. 为什么多了一个 `my::image`

原来的图像能力全在 `my::cv` 里，而 `my::cv` 的第一行就是 `#include <opencv2/core.hpp>`。
板端（Zynq armv7 / PetaLinux）没有 OpenCV，于是这条链在第一步就断了：

```
相机 -> [解码] -> [resize/letterbox] -> [归一化] -> 推理      ← 板端缺前三步
```

`my::image` 只补这一段，依赖是 `core + preprocess + stb`：

| | `my::cv`（OpenCV） | `my::image`（stb） |
|---|---|---|
| 第三方依赖 | OpenCV（几十 MB、需交叉编译） | 两个 `.h` |
| 平台 | x64 + armv7（armv7 用 PetaLinux 2020.2 SDK 交叉编译，见 [05 §8](05-OpenCV接入方案.md)；`dist/` 的 armv7 包里已含 `libmy_cpp_libs_cv.a` 与 `libopencv_*.so`） | 全平台，armv7 可用（零交叉编译负担） |
| 输入类型 | `cv::Mat` | 自己的 `Image`（HWC u8 连续内存） |
| 格式 | OpenCV 支持的全集 | PNG/JPEG/BMP/TGA/GIF（8 bit） |
| 缩放 | `cv::resize`（SIMD 优化） | 自己写的双线性（标量） |
| 什么时候用 | 上位机、需要 HEIF/TIFF/视频 | 板端、吃 V4L2 帧、只做推理前处理 |

两者产出的 `Letterbox` 与张量语义一致，可以互换；但**别在一个工程里混着用**——
颜色顺序的默认值不一样（见 §3.4）。

## 2. 板端链路怎么用

```cpp
#include <my_cpp_libs/image/image.hpp>

my::image::PreprocessSpec spec;
spec.input_width  = 640;
spec.input_height = 640;
spec.keep_aspect  = true;        // letterbox
spec.pad_value    = 114;         // 必须和训练侧一致
spec.norm.scale   = 1.0f / 255.0f;
spec.norm.mean    = {0.485f, 0.456f, 0.406f};
spec.norm.stddev  = {0.229f, 0.224f, 0.225f};
// src_order 默认就是 RGB（stb 解出来就是 RGB），不用改

auto prep = my::image::prepare(frame, spec);      // frame: my::image::Image
if (!prep) { my::log::error("{}", prep.status().to_string()); return; }

auto out = session->run_single_f32(prep.value().tensor, prep.value().shape);
// 后处理拿到框之后：
float box[4] = {...};                              // 模型坐标系
my::image::unletterbox_boxes(box, 1, prep.value().letterbox);
```

完整可跑的例子见 [`examples/07_image_pipeline`](../examples/07_image_pipeline/main.cpp)
（合成一张 640×480 的图 → 编码 → 解码 → letterbox → 推理 → 框映射回原图，
最后一行会打印"期望 (200,140)-(440,340)"，对不上就说明映射算错了）。

## 3. 实现取舍

### 3.1 为什么是 stb，不是 OpenCV / libjpeg-turbo

板端只缺"解码 + 缩放"两件事。为了这两件事把 OpenCV 交叉编译上板，
体积和构建复杂度都不划算（[05-OpenCV接入方案](05-OpenCV接入方案.md) 里估算过）。
libjpeg-turbo 只解决 JPEG，解码速度更好但有构建依赖（CMake + SIMD 汇编）。
stb 的取舍是：**零构建依赖、无异常、单文件**，代价是解码速度（见 §4）
和体积 —— 五个解码器全开时静态库约 220 KB（未 strip，x64），
体积敏感的场景加 `STBI_ONLY_PNG` 之类还能再砍。

### 3.2 关掉了什么

`src/image/stb_impl.cpp` 里定义了 `STBI_NO_PSD/PIC/PNM/HDR`，只保留
PNG/JPEG/BMP/TGA/GIF。需要 PSD/HDR 时把对应 `#define` 去掉即可，不影响 API。

### 3.3 缩放是"点采样式"双线性

放大没问题；**大幅下采样（>2×）会有混叠**，因为没有做面积平均。
相机链路典型是 640×480 → 640×640（放大），够用；如果要 4K → 640，
应该换 `stb_image_resize2.h` 的 `stbir_resize_uint8_srgb`（另一个头文件，
需要一并 pin）。这一点在头文件里也写了，避免有人拿它做缩略图。

### 3.4 颜色顺序：默认值故意和 `my::infer` 不一样

`my::infer::NormalizeSpec` 的默认 `src_order` 是 `BGR`（因为历史上是给
`cv::imread` 用的）。但 stb 解出来是 **RGB**。所以 `my::image::PreprocessSpec`
在自己的默认构造里把它改成了 RGB：

```cpp
infer::NormalizeSpec norm = [] { auto s = infer::NormalizeSpec{}; s.src_order = RGB; return s; }();
```

这不是"魔法"，是为了堵一个具体事故：照抄 cv 的默认值 → R/B 静默互换 →
图看着正常、模型结果全错。同类事故在 [01 §3.4](01-规划与可行性.md) 里已经记了三条。

> 写这条的时候还踩了一个反例（已固化成用例）：`my::cv` 在 4 通道输入上
> 用 `COLOR_BGRA2BGR` 丢 alpha，这个转换**顺带把顺序固定成了 BGR**，
> 于是下游再按 `src_order=RGB` 交换一次 —— 双重交换，R/B 又反回去了。
> 正确做法是丢 alpha 只用"不改顺序"的转换（`BGRA2BGR` / `RGBA2RGB`），
> 顺序的解释权只留在 `image_to_tensor(src_order, dst_order)` 这一处。

### 3.5 letterbox 用的是"取整之后"的缩放比

`letterbox_params()` 给的是理想比例 `min(dst_w/src_w, dst_h/src_h)`，
但实际 resize 的尺寸要取整（`lround`）。两者不一样时，逆变换会累积偏差：
例如 1000×999 → 640×640 时 `new_h = 639`，实际 y 比例是 `639/999 ≈ 0.63964`，
按 `0.64` 逆变换，框越靠下偏得越多。

`my::image::prepare()` 的做法是：先算出整数尺寸，再用
`scale_x = new_w / src_w`、`scale_y = new_h / src_h` **回填** Letterbox。
这样 `unletterbox_box()` 在数学上是精确的（测试里用 100×50 → 64×64
验证了整图映射回 (0,0)-(100,50) 不差一个像素）。

`my::cv::prepare()` 仍然用理想比例（改动会动到已有的 cv 用例），
两者差异在亚像素级；要精确就优先用 `my::image`。

## 4. 实测

> **板端数据（2026-11-16，Zynq-7020 @666MHz）**：`example_image` 跑通 640×480 → letterbox 640×640 →
> 推理 → 映射回原图 (200,140)-(440,340) 与期望一致，**957 ms**（含 PNG 编解码与 stub 推理）；
> `image` 套件 15/15 通过。下面这组是 x64 数据，用来看"哪一步占大头"。

### 4.1 x64 参考（**不是板端数据**）

MinGW GCC 15.2 / `-O3` / 单线程，100 次取平均（`build/bench_image.cpp`，未入库）：

| 输入 | PNG 解码 | JPEG 解码 | `prepare()` → 640×640 |
|---|---|---|---|
| 640×480 | 2.6 ms | 6.0 ms | 5.1 ms |
| 960×720 | 6.4 ms | 15.1 ms | 17.5 ms |
| 1440×1080 | 13.0 ms | 43.8 ms | 22.3 ms |

怎么读这组数：

- **JPEG 比 PNG 慢 2.4~3.4 倍**，因为 stb 的 JPEG 解码是纯标量、没有 SIMD。
- `prepare()` 的大头是**归一化**（每像素每通道一次乘/减/除），不是 resize：
  640×480 → letterbox 到 640×640 时 resize 实际是恒等变换（走快速路径），
  5.1 ms 基本全花在 92 万次浮点运算上。
- **不要把这组数直接除以某个系数当板端结果**。A9 @666MHz 是标量 + 无 NEON 高级指令，
  只能给量级参考：640×480 的 JPEG 解码大概在几十毫秒量级，30 fps 基本不可能。

对板端的结论：

| 相机输出 | 板端怎么办 |
|---|---|
| YUYV/NV12（V4L2 最常见） | 根本不需要 stb，只需要 YUV→RGB 转换（很便宜，**还没实现**） |
| MJPEG | stb 能跑但慢；要 30 fps 就换 libjpeg-turbo（NEON），触发条件：实测 640×480 解码 > 15 ms |
| PNG（离线图片） | stb 够用 |

## 5. `-fno-exceptions`：承诺收窄到"能验证的范围"

### 5.1 原来的问题

[01 §4.2](01-规划与可行性.md) 的 P2 写的是"Zynq 上常以 `-fno-exceptions` 交付"，
但整个工程**没有任何构建选项验证过这件事**，而 `src/` 里有 20 多处 `try/catch`
（json / log / 两个 backend）。真开 `-fno-exceptions`，GCC 会直接报编译错误。

更麻烦的是，用宏把异常关掉也不是解决办法：

| 组件 | 关掉异常后会怎样 |
|---|---|
| `json` | 定义 `JSON_NOEXCEPTION` 才能编过，但解析失败会走 `std::abort()` —— "返回 ParseError"变成"进程没了" |
| `infer` | `Ort::Exception` 必须 catch；`-fno-exceptions` 下 ORT 的 C++ API 编不过 |
| `cv` | OpenCV 用 `cv::Exception`；官方包也是按开异常编的 |
| `log` | `SPDLOG_NO_EXCEPTIONS` 能编过，但"日志文件打不开"会 abort，同样破坏 `Status` 契约 |
| `net` | 自己写的，没有 try/catch（端口解析也从 `std::stol` 换成了手写解析），**可以**进子集 |
| `serial` | 只用 open/read/write/ioctl 与 Status，没有 try/catch，**可以**进子集 |
| `http` | httplib 内部有 throw 路径 + 线程池，不在子集里 |
| `io` | 全部用 `std::filesystem` 的 `error_code` 重载，没有 throw 路径，**可以**进子集（0.1.2 新增） |
| `time` | 只用 `<chrono>` 与 `strftime`；`ScopedTimer` 的 try/catch 按异常开关裁剪，**可以**进子集（0.1.2 新增） |
| `thread` | `std::thread` 构造失败只能靠 `std::system_error` 上报；`std::future` 的 `get()` 也以异常表达失败 —— **不在**子集里（0.1.2 新增） |

也就是说：**"整库 `-fno-exceptions`"这件事做不成，硬做只会把"错误可返回"降级成"错误即崩溃"。**

### 5.2 现在的做法

新增 `-DMYLIB_NO_EXCEPTIONS=ON`，但只对 **core + math + dsp + net + io + time** 承诺
（dsp 用的 pocketfft 在 `Deps.cmake` 里定义了 `POCKETFFT_NO_EXCEPTIONS`，
自己一行 try/catch 都没有），并且在 configure 阶段就把不成立的组合拦下来
（fail-closed，不允许静默降级）：

```powershell
cmake -S . -B build/noex -G Ninja `
  -DMYLIB_NO_EXCEPTIONS=ON `
  -DMYLIB_ENABLE_LOG=OFF -DMYLIB_ENABLE_JSON=OFF `
  -DMYLIB_ENABLE_INFER=OFF -DMYLIB_ENABLE_IMAGE=OFF -DMYLIB_ENABLE_CV=OFF `
  -DMYLIB_ENABLE_HTTP=OFF -DMYLIB_ENABLE_THREAD=OFF
```

> `io` / `time` 不用关：它们不依赖异常上报错误。`thread` 必须关。

如果这时还开着别的组件，configure 直接失败，并打印：

```
MYLIB_NO_EXCEPTIONS=ON 目前只支持 core + math + dsp + net，但以下组件还开着：JSON / INFER
原因：这些组件用异常上报错误（nlohmann / ONNX Runtime / OpenCV / spdlog），
      关掉异常后只能退化成 abort()，会破坏 Status/Result 的契约。
```

**"公共 API 不抛异常"这条不变**（`Status` / `Result<T>` 仍然是唯一的错误通道），
收窄的只是"实现层能不能编成不依赖异常"。

### 5.3 怎么保证它没烂掉

`.github/workflows/ci.yml` 里的 `linux-noexceptions` job 守三件事：

1. 子集能编、能跑测试（122 个用例：core + math + dsp + net + io + time + 框架自测）；
2. `build.ninja` 里**确实**出现了 `-fno-exceptions`（不是只加了个空选项）；
3. 开着 `json` 时必须 configure **失败**，且报错文案正确（防止有人把校验删了）。

## 6. 还没做的

- **YUYV/NV12 → RGB**：板端相机最常见的格式，现在还得业务代码自己做。
  放在 `my::image` 里最合适（`from_yuyv` / `from_nv12`，各 50 行左右）。
- **大倍下采样的面积平均**：见 §3.3，需要换 stb_image_resize2 或自己写 box filter。
- **libjpeg-turbo**：等板端实测 MJPEG 解码不够快再上（见 §4 的触发条件）。
- **10/16 bit 图像**：stb 会降到 8 bit；工业相机常见的 12 bit 需要另想办法。
- **`my::cv` 的 letterbox 精度**：见 §3.5，目前仍是理想比例。
