# 构建与交叉编译

## 1. 环境要求

| 项 | 要求 |
|---|---|
| CMake | ≥ 3.20（本机 4.2.0-rc3） |
| 生成器 | Ninja（交叉/单配置）或 Visual Studio 18 2026（MSVC） |
| C++ | C++17 |
| Python | 仅 `scripts/make_test_model.py` 需要（只用标准库） |

三方库不需要联网：`resources/*.zip` 是唯一真源，首次 configure 自动解压到 `third_party/`。
想强制重新解压就删掉 `third_party/` 或加 `-DMYLIB_AUTO_EXTRACT_DEPS=ON`。

## 2. 五个预设

| 预设 | 目标 | 编译器 | 产物 | 能否运行 |
|---|---|---|---|---|
| `win-msvc` | Windows x64 | MSVC 19.50 (VS 2026) | PE x64 | ✅ 本机 |
| `win-mingw` | Windows x64 | MinGW-w64 GCC 15.2 | PE x64 | ✅ 本机 |
| `linux-x64` | Linux x86_64 | GCC 9.3 / glibc 2.31 | ELF x86-64 | 需 Linux 环境 |
| `linux-armv7` | Linux armv7-A HF | GCC 13.3 (PetaLinux SDK) | ELF ARM EABI5 HF | 需 Zynq 板 |
| `linux-aarch64` | Linux aarch64 | GCC 14.2 (ARM GNU) | ELF AArch64 | 需 ARM64 板 |

```powershell
cmake --preset <name>
cmake --build --preset <name>

# 一次性全跑（含宿主平台的 ctest、交叉平台的编译验证）
.\scripts\build-all.ps1
```

产物：`build/<preset>/bin/`。VS 多配置在 `build/win-msvc/bin/Release/`。

## 3. 各工具链说明

### 3.1 linux-x64（`cmake/toolchains/linux-x64-gcc9.cmake`）

来源：`D:\ProgramData\x86_64-linux-gnu\gcc-9.3.0`（VisualGDB 打包的 Ubuntu 20.04 交叉工具链）。

**两个必须加的参数**，否则链接失败：

```
-mstack-protector-guard=tls   # 否则 undefined reference to `__stack_chk_guard'
-fno-pie / -no-pie            # 该 sysroot 默认 PIE，交叉 gcc 默认非 PIE
```

sysroot：`<root>/x86_64-linux-gnu/sysroot`（glibc 2.31）。

### 3.2 linux-armv7（`cmake/toolchains/linux-armv7-zynq.cmake`）

来源：`D:\ProgramData\gcc-arm-linux-gnueabi`（PetaLinux SDK，GCC 13.3.0）。

```
-march=armv7-a -mcpu=cortex-a9 -mfpu=neon -mfloat-abi=hard
```

sysroot：`<root>/cortexa9t2hf-neon-xilinx-linux-gnueabi`。

产物校验（已确认）：

```
ELF 32-bit, machine = ARM(40), e_flags & EF_ARM_ABI_FLOAT_HARD != 0, EABI5
```

> 若你的板子是 ZynqMP（Cortex-A53），用 `linux-aarch64` 而不是这个预设。

### 3.3 linux-aarch64（`cmake/toolchains/linux-aarch64.cmake`）

来源：ARM GNU Toolchain 14.2.1。

**坑**：sysroot 在 `<prefix>/aarch64-none-linux-gnu/libc`，不是 `<prefix>`；
指向错的位置会报 `cannot find crt1.o / -lm`。

自带 glibc 较新（约 2.40）。**如果目标板系统更老，必须把 sysroot 换成板子 SDK 的**：

```powershell
cmake --preset linux-aarch64 -DMYLIB_TARGET_SYSROOT=D:/path/to/board/sysroot
```

### 3.4 win-msvc

用 Visual Studio 生成器（多配置），不需要手动进 `vcvars`：

```powershell
cmake --preset win-msvc
cmake --build --preset win-msvc            # 默认 Release
```

> 若想用 Ninja + MSVC，需要先进入 VS 开发者环境（`vcvars64.bat` 或
> `Enter-VsDevShell`），否则 `cl.exe` 不在 PATH 里。这是 CMake 的限制，不是本项目的。

### 3.5 win-mingw

预设里已经把 `D:\ProgramFiles\msys64\ucrt64\bin` 加到 PATH，
`CMAKE_MAKE_PROGRAM` 显式指向 Ninja，避免 MSYS2 自带 ninja 版本冲突。

## 4. 测试模型

`models/identity_1x1x4.onnx` 是一个 120 字节的最小 ONNX 模型（`y = Identity(x)`，输入输出都是 `f32[1,1,4]`），
用来验证推理链路能真正加载模型并跑出结果。

它是脚本手写 protobuf 生成的，不依赖 `onnx` / `protobuf` 包：

```powershell
python scripts/make_test_model.py models/identity_1x1x4.onnx
```

跑一遍真实推理（需要 MSVC 构建，因为只有它能链接 ORT）：

```powershell
.\build\win-msvc\bin\Release\example_infer.exe models\identity_1x1x4.onnx
# 编译期后端: onnxruntime | 已注册: stub, onnxruntime
# 使用后端: onnxruntime
#   - x  type=f32 shape=[1, 1, 4]
# 前几个值: 1.0000 2.0000 3.0000 4.0000
```

## 5. 上板部署（Zynq 为例）

> 完整流程见 [板端验证手册](06-板端验证手册.md)，这里只列最关键的几步。


```powershell
# 1. 构建
cmake --preset linux-armv7
cmake --build --preset linux-armv7

# 2. 看依赖
#    产物是静态链接 my_cpp_libs + spdlog，动态依赖只有 libstdc++/libgcc/libc/libpthread/librt/libm
```

拷贝到板子（任选其一）：

```powershell
scp build\linux-armv7\bin\mylib_tests root@<board-ip>:/tmp/
scp build\linux-armv7\bin\example_log root@<board-ip>:/tmp/
# 或走 NFS / SD 卡
```

板上运行：

```bash
chmod +x /tmp/mylib_tests
/tmp/mylib_tests
```

**如果报 `GLIBC_2.xx not found`**：说明板上 glibc 比 SDK 里的旧。
解决办法是把 `MYLIB_TARGET_SYSROOT` 指向板子自己的 sysroot 再重编，而不是去折腾板子的库。

**如果报 `libstdc++.so.6: version GLIBCXX_3.4.3x not found`**：同理，
GCC 13.3 的 libstdc++ 比板上新。两个选择：

1. 用板子 SDK 对应的老工具链重编；
2. 静态链接 libstdc++：`-DCMAKE_EXE_LINKER_FLAGS="-static-libstdc++ -static-libgcc"`。

推荐 2，对嵌入式最省事。

## 6. 踩坑记录（含复现与解释）

### 5.1 `__stack_chk_guard` 未定义

```
undefined reference to `__stack_chk_guard'
```

Ubuntu 系工具链默认 `-mstack-protector-guard=tls`，而这套交叉 gcc 默认是非 TLS 的。
两边的符号名不同。加 `-mstack-protector-guard=tls` 即可。

### 5.2 `cannot find crt1.o`

见 §3.3。ARM GNU Toolchain 的 sysroot 在 `libc/` 子目录。

### 5.3 静态库里"自注册"失效

```cpp
// 看着没问题，实际可能根本不执行
struct Registrar { Registrar() { register_backend("x", make_x); } };
const Registrar g_registrar;
```

静态库链接时，如果某个 `.o` 里没有任何被引用的符号，链接器会**整个丢掉**，
静态对象自然不会构造。日志看起来就是"后端没注册"。

本项目改成显式调用：

```cpp
void ensure_builtin_backends() {
    static std::once_flag flag;
    std::call_once(flag, [] {
        detail::register_stub_backend();
#if defined(MYLIB_HAVE_ONNXRUNTIME)
        detail::register_onnxruntime_backend();
#endif
    });
}
```

### 5.4 `-DXXX="0.1.0"` 在 gcc 上被吃掉引号

CMake 在 Windows 上对命令行的引号转义，Ninja 和 MSVC 处理方式不同。
gcc 收到的是 `-DMYLIB_VERSION_STR=0.1.0`，于是报 `too many decimal points in number`。

解决：改用 `configure_file` 生成头文件（`src/core/build_info_config.h.in`）。
**这是跨平台工程里的通用建议：字符串宏一律用生成头，不要走命令行。**

### 5.5 `format()` 重载歧义

```cpp
namespace my::log {
template <class... Args> std::string format(fmt::format_string<Args...>, Args&&...);
template <class... Args> void info(fmt::format_string<Args...> f, Args&&... a) {
    write(Level::Info, format(f, a...));   // 编译错误：ambiguous
}
}
```

参数里有 `fmt::format_string`，ADL 会把 `fmt::format` 拉进候选集。写成 `::my::log::format(...)`。

### 5.6 `add_library(deps::spdlog ALIAS spdlog::spdlog)` 报错

CMake 不允许给 ALIAS 目标再起别名。套一层：

```cmake
add_library(deps_spdlog INTERFACE)
target_link_libraries(deps_spdlog INTERFACE spdlog::spdlog)
add_library(deps::spdlog ALIAS deps_spdlog)
```

### 5.7 不要用 INTERFACE 编译定义改三方库行为

曾经给 `deps::json` 加过 `JSON_USE_IMPLICIT_CONVERSIONS=0`，
结果所有消费方（包括演示"原生 API 怎么写"的示例）都编不过了。

**规则**：三方库的默认行为不要动；要改就在自己的 `src/` 里改。

## 7. 在自己的工程里使用

### 方式 A：源码嵌入（推荐）

```cmake
add_subdirectory(third_party/my_cpp_libs my_cpp_libs_build)

target_link_libraries(app PRIVATE
    my_cpp_libs::log
    my_cpp_libs::json)
```

完整可运行示例：`examples/consumer_app/`

```powershell
cmake -S examples/consumer_app -B build/consumer_app -G Ninja `
      -DCMAKE_C_COMPILER=D:/ProgramFiles/msys64/ucrt64/bin/gcc.exe `
      -DCMAKE_CXX_COMPILER=D:/ProgramFiles/msys64/ucrt64/bin/g++.exe
cmake --build build/consumer_app
```

优点：跟着你的工具链编，天然 ABI 一致；可以只开需要的组件。

### 方式 B：安装后用

```powershell
cmake --install build/win-mingw --prefix D:/sdk/my_cpp_libs
```

会装头文件和静态库。**注意**：`find_package` 的导出配置留到 M4，
现在需要手工 `include_directories` + `link_directories`。
在跨多个工具链的场景下，方式 A 明显更省事。

## 8. 常用选项

| 选项 | 默认 | 说明 |
|---|---|---|
| `MYLIB_BUILD_EXAMPLES` | 顶层工程 ON | 构建示例 |
| `MYLIB_BUILD_TESTS` | 顶层工程 ON | 构建单元测试 |
| `MYLIB_ENABLE_LOG` | ON | spdlog 组件 |
| `MYLIB_ENABLE_JSON` | ON | nlohmann 组件 |
| `MYLIB_ENABLE_MATH` | ON | Eigen 组件 |
| `MYLIB_ENABLE_INFER` | ON | 推理组件（无 ORT 时用 stub） |
| `MYLIB_ENABLE_NCNN` | OFF | 接入 ncnn 备选后端 |
| `MYLIB_ENABLE_CV` | OFF | 图像组件（需要 OpenCV） |
| `MYLIB_NCNN_ROOT` | 自动搜索 | ncnn 安装根目录 |
| `MYLIB_OPENCV_ROOT` | 自动搜索 | OpenCV 的 `OpenCV_DIR`（含 OpenCVConfig.cmake 的目录） |
| `MYLIB_BUILD_SHARED` | OFF | 构建动态库 |
| `MYLIB_ONNXRUNTIME_ROOT` | 自动搜索 | ONNX Runtime 预编译包根目录 |
| `MYLIB_DEPS_DIR` | `third_party` | 解压目标目录 |
| `MYLIB_AUTO_EXTRACT_DEPS` | ON | 自动解压 |

例：Zynq 上只要日志，把体积压到最小：

```powershell
cmake --preset linux-armv7 `
  -DMYLIB_ENABLE_JSON=OFF -DMYLIB_ENABLE_MATH=OFF -DMYLIB_ENABLE_INFER=OFF `
  -DMYLIB_BUILD_EXAMPLES=OFF -DMYLIB_BUILD_TESTS=OFF
```

## 9. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| configure 卡在 `Performing Test ...` | 交叉编译的 `try_compile` 需要实际调编译器 | 正常，首次会慢几秒 |
| `ninja: error: loading 'build.ninja'` | configure 失败导致没有生成 | 先看 configure 的报错 |
| 找不到 `cl.exe` | 用的是 Ninja + MSVC 但没进 VS 环境 | 用 `win-msvc` 预设（VS 生成器）或先 `vcvars64.bat` |
| `spdlog` 重复定义 | 你的工程里还链接了另一份 spdlog | 用 `SPDLOG_HEADER_ONLY` 或统一用本项目的 `deps::spdlog` |
| 修改 CMake 后行为没变 | 缓存里还是旧值 | 删掉 `build/<preset>` 重来 |
| 交叉编译的单测没法跑 | 目标机架构不同 | 正常，交叉编译时只构建不注册 CTest |
