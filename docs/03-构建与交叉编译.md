# 构建与交叉编译

## 1. 环境要求

| 项 | 要求 |
|---|---|
| CMake | ≥ 3.23（走 `CMakePresets.json`；本机 4.2.0） |
| 生成器 | Ninja（交叉/单配置）或 Visual Studio 18 2026（MSVC） |
| C++ | C++17 |
| Python | 仅 `scripts/make_test_model.py` 需要（只用标准库） |

三方库不需要联网：`resources/*.zip` 是唯一真源，首次 configure 自动解压到 `third_party/`。
想强制重新解压就删掉 `third_party/` 或加 `-DMYLIB_AUTO_EXTRACT_DEPS=ON`。

## 2. 预设一览

Windows 主机可见的预设：

| 预设 | 目标 | 编译器 | 产物 | 能否运行 |
|---|---|---|---|---|
| `win-msvc` | Windows x64 | MSVC 19.50 (VS 2026) | PE x64 | ✅ 本机 |
| `win-mingw` | Windows x64 | MinGW-w64 GCC 15.2 | PE x64 | ✅ 本机 |
| `win-ubsan` | Windows x64 | 同上 + UBSan(trap) | PE x64 | ✅ 本机 |
| `linux-x64` | Linux x86_64 | GCC 9.3 / glibc 2.31 | ELF x86-64 | 需 Linux 环境 |
| `linux-armv7` | Linux armv7-A HF | GCC 13.3 / 2024 SDK，**glibc 2.39** | ELF ARM EABI5 HF | ⚠️ **仅编译验证**，板子 glibc 需 ≥2.38 |
| `linux-armv7-static` | Linux armv7-A HF | 同上 + `-static` | ELF ARM，自带 libc | ✅ 板子不依赖任何库 |
| `linux-aarch64` | Linux aarch64 | GCC 14.2 (ARM GNU) | ELF AArch64 | 需 ARM64 板 |

只在 Linux 主机上可见（SDK/apt 工具链在 Linux 上）：

| 预设 | 用途 |
|---|---|
| `linux-armv7-sdk2020` | 板子配套 PetaLinux 2020.2 SDK（glibc 2.30）—— 上板正解 |
| `linux-armv7-cross` | apt 的 `arm-linux-gnueabihf-gcc`，CI 用，只做编译验证 |
| `linux-aarch64-cross` | apt 的 `aarch64-linux-gnu-gcc`，CI 用 |

> **三份 armv7 预设不要混用**：它们的区别就是 glibc 版本。
> 板子是 PetaLinux 2020.2（glibc 2.30），`linux-armv7` 编出来的动态产物上板会报
> `GLIBC_2.38 not found` —— 这是"编译通过 ≠ 能部署"的典型陷阱。

```powershell
cmake --preset <name>
cmake --build --preset <name>

# 一次性全跑（含宿主平台的 ctest、交叉平台的编译验证）
.\scripts\build-all.ps1

# 本机跑一遍 CI 等价检查：默认 / UBSan / 最小配置 / MSVC
.\scripts\ci-local.ps1
```

产物：`build/<preset>/bin/`。VS 多配置在 `build/win-msvc/bin/Release/`。

## 3. 各工具链说明

### 3.1 linux-x64（`cmake/toolchains/linux-x64-gcc9.cmake`）

来源：`D:\ProgramData\x86_64-linux-gnu\gcc-9.3.0`（VisualGDB 打包的 Ubuntu 20.04 交叉工具链）。

**两个必须加的参数**，否则链接失败：

```
-mstack-protector-guard=tls   # 否则 undefined reference to `__stack_chk_guard'
-fno-pie / -no-pie            # 该 sysroot 默认 PIE，交叉 gcc 默认非 PIE
```

sysroot：`<root>/x86_64-linux-gnu/sysroot`（glibc 2.31）。

### 3.2 linux-armv7（`cmake/toolchains/linux-armv7-zynq.cmake`）

来源：`D:\ProgramData\gcc-arm-linux-gnueabi`（**2024 版** SDK，GCC 13.3.0，sysroot glibc 2.39）。

```
-mcpu=cortex-a9 -mfpu=neon -mfloat-abi=hard
```

> 只写 `-mcpu`：它已经隐含 `armv7-a + NEON`。同时再写 `-march=armv7-a` 会被 GCC 规范化成
> `armv7-a+simd`，然后**每个编译单元报一条** `switch '-mcpu=cortex-a9' conflicts with
> switch '-march=armv7-a+simd'` —— 曾经每轮全量构建固定 35 条噪声。

sysroot：`<root>/cortexa9t2hf-neon-xilinx-linux-gnueabi`。

产物校验（已确认）：

```
ELF 32-bit, machine = ARM(40), e_flags & EF_ARM_ABI_FLOAT_HARD != 0, EABI5
```

⚠️ **glibc 2.39 的产物不能在 PetaLinux 2020.2（glibc 2.30）的板子上跑**。
上板用 `linux-armv7-static`（全静态）或 `linux-armv7-sdk2020`（配套 SDK），见 §5。

> 若你的板子是 ZynqMP（Cortex-A53），用 `linux-aarch64` 而不是这个预设。

### 3.3 linux-aarch64（`cmake/toolchains/linux-aarch64.cmake`）

来源：ARM GNU Toolchain 14.2.1。

**坑**：sysroot 在 `<prefix>/aarch64-none-linux-gnu/libc`，不是 `<prefix>`；
指向错的位置会报 `cannot find crt1.o / -lm`。

自带 glibc 较新（约 2.40）。**如果目标板系统更老，必须把 sysroot 换成板子 SDK 的**：

```powershell
cmake --preset linux-aarch64 -DMYLIB_TARGET_SYSROOT=D:/path/to/board/sysroot
```

**两个交叉编译的坑（都踩过）**：

1. **`CMAKE_TOOLCHAIN_FILE` 要给绝对路径**：CMake 4.2 把相对路径按*构建目录*解析，
   报错却是 `CMAKE_CXX_COMPILER not set, after EnableLanguage`，完全看不出根因。
   预设里写的是 `${sourceDir}/...` 绝对路径，直接 `--preset` 没这个问题。
2. **`-no-pie` 只能给可执行文件**：加到共享库链接参数上，链接器会去找 `crt1.o` 的
   `_start`，报 `undefined reference to 'main'`（交叉编 OpenCV 的 `.so` 时踩到）。
   工具链文件里已经只给 `CMAKE_EXE_LINKER_FLAGS_INIT`。

**交叉编 OpenCV 时额外要加** `-DCMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY`，
否则 OpenCV 的探测性 `try_compile` 也会撞同一个 `main` 问题。
本项目在 Windows 上交叉编 aarch64 时，OpenCV 的 ELF 安装树会被 Windows 分支的
"ELF 过滤"跳过，所以必须显式给 `-DMYLIB_OPENCV_ROOT=<install>/lib/cmake/opencv4`。

### 3.4 win-msvc

用 Visual Studio 生成器（多配置），不需要手动进 `vcvars`：

```powershell
cmake --preset win-msvc
cmake --build --preset win-msvc            # 默认 Release
```

> 若想用 Ninja + MSVC，需要先进入 VS 开发者环境（`vcvars64.bat` 或
> `Enter-VsDevShell`），否则 `cl.exe` 不在 PATH 里。这是 CMake 的限制，不是本项目的。

### 3.5 win-mingw

预设里已经把 `D:\ProgramFiles\msys64\ucrt64\bin` 加到 PATH，
`CMAKE_MAKE_PROGRAM` 显式指向 Ninja，避免 MSYS2 自带 ninja 版本冲突。

### 4.1 单元测试怎么跑

**逐用例注册**：用例名在 configure 期直接从源码的 `MYTEST_CASE(<name>)` 扫出来，
所以 `ctest` 看到的是 199 个独立测试项（开启 OpenCV 时 207 个）+ 2 个自检项（`mylib_list_cases`、
失败直接定位到具体用例，也能 `ctest -j` 真正并行。

```powershell
ctest --preset win-mingw                     # 全部
ctest --preset win-mingw -R preprocess       # 只跑 preprocess 那批
ctest --preset win-mingw -R nms -V           # 单个/少量用例，看完整输出
ctest --preset win-mingw -j 8                # 并行
```

测试二进制自己也能过滤（调试单个用例时更快）：

```powershell
build\win-mingw\bin\mylib_tests --list              # 列出 suite:name
build\win-mingw\bin\mylib_tests --case=preprocess_nms   # 名字必须完全一致，找不到会报错退出
build\win-mingw\bin\mylib_tests --suite=preprocess      # 整个套件
build\win-mingw\bin\mylib_tests --filter=nms            # 按子串
```

用例失败是"记一条 FAIL 继续跑下一个"，不会因为一条断言就丢掉后面所有用例
（`Result::value()` 在失败状态被调用仍会 abort，但会先往 stderr 打一行原因）。

> 为什么在 configure 期扫源码而不是运行 `--list`：交叉编译时目标二进制根本跑不起来；
> 静态扫描既没有这个限制，也避免"测试配置晚一轮才出现"。代价是用例改名后必须重新
> configure —— `--case=` 找不到名字时会直接报错，不会静默通过。

### 4.2 消毒器（UBSan / ASan）

```powershell
cmake --preset win-ubsan
cmake --build --preset win-ubsan
ctest --preset win-ubsan
```

实现上走 `-fsanitize=undefined -fsanitize-undefined-trap-on-error`：UB 编译成 trap 指令，
**不需要 libubsan**，所以 MinGW（没有 libubsan）和交叉编译也能开。
代价是只有"过/不过"而没有详细报告 —— 定位问题时在 Linux 上跑一遍 ASan 版即可。

```bash
# Linux / CI：内存错误 + 泄漏
cmake -S . -B build/asan -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo -DMYLIB_SANITIZE=address
cmake --build build/asan && ctest --test-dir build/asan --output-on-failure
```

### 4.3 CI

`.github/workflows/ci.yml` 覆盖：Linux 全组件 / UBSan / ASan / 最小配置（只留 core+log+image+dsp+net，99 用例）/
**`-fno-exceptions` 子集** / armv7 与 aarch64 交叉编译 / Windows MSVC / Windows MinGW+UBSan。

两个 Windows job 以前**没有 fetch-deps**：`resources/*.zip` 不进 git，所以一跑就会在
`[deps] Eigen 头文件缺失` 处 FATAL_ERROR。现在都补了缓存 + `scripts/fetch-deps.ps1`
（MinGW job 的默认 shell 是 msys2，那一步显式用 `shell: pwsh`）。

缓存 key 带上了 `hashFiles('scripts/fetch-deps.*')`：改了下载地址/版本会自动失效，
不会拿着旧缓存去骗自己。

### 4.3.1 `-fno-exceptions` job

```bash
cmake -S . -B build/noex -G Ninja \
  -DMYLIB_NO_EXCEPTIONS=ON \
  -DMYLIB_ENABLE_LOG=OFF -DMYLIB_ENABLE_JSON=OFF \
  -DMYLIB_ENABLE_INFER=OFF -DMYLIB_ENABLE_IMAGE=OFF -DMYLIB_ENABLE_CV=OFF \
  -DMYLIB_ENABLE_HTTP=OFF -DMYLIB_ENABLE_THREAD=OFF
```

> `THREAD` 必须关：`std::thread` 构造失败只能靠 `std::system_error` 上报；
> `io` / `time` 不用关（它们只用 `error_code` 与 `chrono`）。

这个 job 守三件事（任何一条退化成"看起来支持"都会被抓住）：

1. 子集能编、151 个用例能跑（core + math + dsp + net + io + time + serial + 框架自测）；
2. `build.ninja` 里确实有 `-fno-exceptions`（防止选项变成空开关）；
3. 开着 json 时必须 **configure 失败**，且报错里要出现"只支持 core + math + dsp + net + io + time"
   （防止有人把校验删了、把承诺又写回文档）。

CI 里**不用 CMakePresets**——预设里的工具链路径是本机绝对路径，CI 上不存在；
CI 直接给 `-D` 参数，这也顺带验证了"不依赖预设也能构建"。
依赖由 `scripts/fetch-deps.sh` 从上游下载（`resources/*.zip` 不进 git）。

想在本机复现 CI 的 Windows 部分：

```powershell
.\scripts\ci-local.ps1
```

### 4.3.2 `linux-debug`：唯一构建 Debug 的 job

Reason：`Release / RelWithDebInfo / MinSizeRel` 都会定义 `NDEBUG`，于是

- Eigen / STL 的 `assert` 不会被编译进去；
- 我们自己写在实现里的前置条件检查也一起消失。

后果是"一类只在 Debug 下暴露的缺陷，在 CI 里永远是绿的"。真实案例：`least_squares()`
把矩阵喂给了 `Eigen::Ref<const VecXd>` 形参，Release 下靠连续内存"侥幸正确"，
Debug 下必崩（`Ref.h:133` 的 `rows()==1 || cols()==1`），而当时 CI 全是 Release 家族 +
一个用 `RelWithDebInfo` 的 ASan job —— 三道关都没拦住。

所以现在：

- `linux-debug` 用 `-DCMAKE_BUILD_TYPE=Debug` 全量构建并跑 ctest；
- `linux-asan` 的构建类型也从 `RelWithDebInfo` 改成 `Debug`，与
  `scripts/run-tests-asan-wsl.sh` 对齐。

### 4.3.3 `linux-sdk-consumer`：验证 `find_package` 这条腿

`add_subdirectory` 用法一直有 `examples/consumer_app` 守着，但**SDK 用法没有**。
这个 job 做完整链路：

```bash
cmake -S . -B build/ci-sdk -G Ninja -DCMAKE_BUILD_TYPE=Release \
      -DMYLIB_BUILD_EXAMPLES=OFF -DMYLIB_BUILD_TESTS=OFF -DMYLIB_BUILD_TOOLS=OFF \
      -DCMAKE_INSTALL_PREFIX="$PWD/sdk"
cmake --build build/ci-sdk && cmake --install build/ci-sdk
cmake -S tests/sdk_consumer -B build/consumer -G Ninja -DCMAKE_PREFIX_PATH="$PWD/sdk"
cmake --build build/consumer && ./build/consumer/sdk_consumer
```

`tests/sdk_consumer/CMakeLists.txt` **刻意不设** `CMAKE_CXX_STANDARD`：
公共头要求 C++17，这个要求必须由 `my_cpp_libsConfig.cmake` 的
`INTERFACE_COMPILE_FEATURES` 传过来。丢了这一条，下游默认 C++14 的工程就会编不过 ——
这正是 0.1.1 修掉的缺陷之一，现在由这个 job 永久守住。

### 4.3.4 `linux-tsan`：数据竞争

`log` 的全局状态、`infer` 的后端注册表、`http` 的线程管理都在文档里写着"线程安全"，
但在 0.1.1 之前**一个并发用例都没有**。`MYLIB_SANITIZE=thread` 会在
`-fsanitize=thread` 下构建并跑一遍全部用例。

注意 Ubuntu 24.04 的 `vm.mmap_rnd_bits=32` 会让 TSan 直接报
`unexpected memory mapping`（与代码无关），CI 里先 `sysctl -w vm.mmap_rnd_bits=28`。

### 4.3.5 `qemu-test`：ARM 单测**真的跑一遍**

`cross` job 只验证"能编能链"——这是 0.1.3 之前"5 平台"里 ARM 的全部证据。
`qemu-test` 用 qemu-user 把它补成"真跑"：

| 目标 | qemu | 说明 |
|---|---|---|
| armv7 | `qemu-arm-static` | apt 的 `gcc-arm-linux-gnueabihf` 交叉编译 |
| aarch64 | `qemu-aarch64-static` | apt 的 `gcc-aarch64-linux-gnu` |

三个关键做法（都是踩过的坑）：

1. **产物链接成全静态**（`-DCMAKE_EXE_LINKER_FLAGS=-static`），
   于是 `qemu-*-static ./mylib_tests` 直接执行，**不需要 `-L <sysroot>`**。
   动态链接的话 qemu 会抱怨找不到 `libstdc++.so.6`/`ld-linux-armhf.so.3`，
   而 sysroot 路径又要按 triple 猜——静态链接把这一整类问题消掉。
   本地已用两套工具链验证过产物 `readelf -d` 输出 "no dynamic section"
   （armv7 4.45 MB / aarch64 19.7 MB）。
2. **不注册 binfmt**：直接把 `qemu-*-static` 当解释器调用，
   避开 `update-binfmts` 的权限问题（CI 里 sudo 能用但容易受镜像限制）。
3. **整包一次跑**，不是逐用例 261 个进程：qemu 下进程启动开销比测试本身还大。

job 里还有一道**防退化检查**：`readelf -d | grep NEEDED` 命中就判定失败，
否则"`-static` 悄悄失效"会让这个 job 变成一堆看不懂的 qemu 报错。

失败判定看两处：进程退出码（框架失败时返回非 0）+ 汇总行里"失败用例数"必须为 0。
`[SKIP]` 是允许的（交叉构建没有 ORT 时 `ml` 的对拍会跳过）。

> 本机没有 qemu（WSL 也装不了，无外网），所以这个 job **没在本地跑过**，
> 首跑需要看 CI 日志。但它做的每一步本地都单独验证过：交叉编译通过、产物全静态、
> 用例数与注册表一致。

### 4.4 打包：CPack（`dist/` 里的包怎么来的）

0.1.0/0.1.1 的四个 SDK 包是**手工装的**：没有打包脚本、`dist/` 被 gitignore、
包内也没有许可证。评估报告把这条列为"不可重建、不可溯源、合规缺失"（C1/C2）。
0.1.2 起改成 CPack：

```text
cmake/Packaging.cmake
  ├─ 安装许可证：我们的 MIT + 每个三方依赖的原始 LICENSE
  │    · stb / pocketfft 没有独立 LICENSE 文件（声明在头文件里），
  │      直接把源文件装进 share/licenses/my_cpp_libs/sources/ —— 原样保留最不容易出错
  │    · 缺任何一份会打印 `[pkg] 找不到许可证 ...`（这条就是发布前的红灯）
  ├─ 设 CPACK_PACKAGE_FILE_NAME = my_cpp_libs-<版本>-<suffix>
  │    suffix 由 -DMYLIB_PACKAGE_SUFFIX 显式给，默认按 平台-架构-编译器 推
  └─ include(CPack)            → 生成 CPackConfig.cmake
```

三条设计约束：

1. **包名后缀必须显式**。glibc 版本 CMake 推不出来，而"用 2.39 编的包装到
   2.30 的板子上"是最容易犯的错（`GLIBC_2.xx not found`）。所以板端包的后缀
   一律写成 `linux-armv7-glibc230` 这种形式，由构建者负责。
2. **包内容 = install 树**。CPack 不重新挑文件，直接打包 `cmake --install` 的结果，
   所以"能 install 就能打包"，两条路径不会分叉。
3. **构建身份进包**。`CPACK_PACKAGE_DESCRIPTION` 里带 git commit、编译器、构建类型、
   组件清单 —— 拿到一个包不用猜它是哪次构建。

验证一个包（把包解开、用里面的 Config 编一个外部工程、跑起来）：

```powershell
.\scripts\package-all.ps1                                   # 本机出四个全量包 → dist/
.\scripts\verify-package.ps1 -Package dist\my_cpp_libs-0.1.4-win-x64-msvc.zip
```

CI 里的 `linux-sdk-consumer` job 做的是同一件事，只是直接从构建树 install，
不是从压缩包 —— 两者互补：前者守 install 规则，后者守"解压之后仍然可用"。

#### 4.4.1 CI 打包 job（0.1.5 起）

0.1.3~0.1.4 的四个包一直是**本机**跑 `package-all.ps1` 生成的 —— 也就是"发版依赖这台
机器恰好装了四套工具链"。0.1.5 加了两个 job 把同一套 CPack 流程搬进 CI：

| job | 矩阵 | 依赖 | 产物 | 包名后缀 |
|---|---|---|---|---|
| `package-linux` | armv7 / aarch64 | apt 交叉工具链 | `.tar.gz` | `linux-<arch>-glibc<NNN>-basic` |
| `package-windows` | MSVC | fetch-deps（含 ORT，无 OpenCV） | `.zip` | `win-x64-msvc-ort` |

（`package-all.ps1` / `verify-package.ps1` 已从被 gitignore 的 `assess/` 移进 `scripts/`，
现在脚本本身也进仓库了。）

两个 job 的验收方式一致：**cpack → 解包 → 用包里的 Config 编一个外部工程**。
Linux 侧因为不能运行，只做"交叉编译 + 链接"；Windows 侧还会把 `sdk_consumer` 真跑一遍。

包名后缀里的 `basic` / `ort` 不是装饰：CI 拿不到 OpenCV 的交叉/Windows 预编译包（体积大、
不进 `fetch-deps`），所以 CI 出的包不含 OpenCV，命名必须如实反映，否则"下了一个 0.1.5
的 msvc 包却没有 cv 组件"会变成一场排查。

> 由此保留两条路并行：**全量包**（ORT+OpenCV+ncnn）仍由本机 `package-all.ps1` 生成并
> 作为 release 资产；**CI 包**用来证明"打包配方本身是可复现的"，同时也是 PR 级别的
> 打包回归（改坏了 install 规则，CI 当场红）。

> 已知缺口：`linux-armv7-sdk2020`（PetaLinux 2020.2 / glibc 2.30）的包需要那套 SDK，
> 本机没有，所以 0.1.2 只出了 glibc 2.39 的 armv7 包，并在 README 里写明上不了 2.30 的板子。
> 有 SDK 的机器上执行同一套 `cpack` 命令、把后缀改成 `linux-armv7-glibc230` 即可。

### 4.5 发布（`scripts/release.ps1`）

0.1.0 的四个包是**手工上传**的：流程没留痕、换台机器就复现不出来。现在一条命令：

```powershell
$env:GH_TOKEN = '<fine-grained PAT>'   # 不要写进任何文件
.\scripts\release.ps1                  # 推送 main+tag → 建 release → 上传 → 核对
.\scripts\release.ps1 -DryRun          # 只看会做什么
.\scripts\release.ps1 -SkipPush        # 代码已推过，只发 release
```

它做四件事：读 `CMakeLists.txt` 的版本号 → 推 `main` 与 `v<版本>` →
用 CHANGELOG 里对应章节当 release notes 建 release → 上传 `dist/` 下匹配本版本的文件
（已存在且大小一致则跳过，上传后校验字节数，最后再拉一次 release 核对没有漏传）。

**token 权限要求**（踩过一次）：

| 权限 | 为什么需要 |
|---|---|
| Contents: Read and write | 推送提交 / 建 release / 传产物 |
| **Workflows: Read and write** | 仓库里有 `.github/workflows/`；缺这个权限时，任何改动工作流文件的提交都会被 GitHub 拒绝，报 `refusing to allow a Personal Access Token to create or update workflow ... without workflow scope` |

另外本机有个坑：`git config http.proxy = http://127.0.0.1:7897`，而 Git for Windows 默认的
schannel 走这个代理会 `SSL/TLS handshake` 失败。脚本里对 git 用了
`-c http.sslBackend=openssl`（拔掉代理反而是另一条路：`git config --unset http.proxy`）。

## 5. 上板部署（Zynq 为例）

> 完整流程见 [板端验证手册](06-板端验证手册.md)，这里只列最关键的几步。


```powershell
# 1. 构建（板子 glibc 2.30，必须用静态版或用配套 SDK，见 §3.2 的警告）
cmake --preset linux-armv7-static
cmake --build --preset linux-armv7-static

# 2. 看依赖
#    产物是静态链接 my_cpp_libs + spdlog，动态依赖只有 libstdc++/libgcc/libc/libpthread/librt/libm
```

拷贝到板子（任选其一）：

```powershell
scp build\linux-armv7\bin\mylib_tests root@<board-ip>:/tmp/
scp build\linux-armv7\bin\example_log root@<board-ip>:/tmp/
# 或走 NFS / SD 卡
```

板上运行：

```bash
chmod +x /tmp/mylib_tests
/tmp/mylib_tests
```

**如果报 `GLIBC_2.xx not found`**：说明板上 glibc 比 SDK 里的旧。
解决办法是把 `MYLIB_TARGET_SYSROOT` 指向板子自己的 sysroot 再重编，而不是去折腾板子的库。

**如果报 `libstdc++.so.6: version GLIBCXX_3.4.3x not found`**：同理，
GCC 13.3 的 libstdc++ 比板上新。两个选择：

1. 用板子 SDK 对应的老工具链重编；
2. 静态链接 libstdc++：`-DCMAKE_EXE_LINKER_FLAGS="-static-libstdc++ -static-libgcc"`。

推荐 2，对嵌入式最省事。

## 6. 踩坑记录（含复现与解释）

### 6.1 `__stack_chk_guard` 未定义

```
undefined reference to `__stack_chk_guard'
```

Ubuntu 系工具链默认 `-mstack-protector-guard=tls`，而这套交叉 gcc 默认是非 TLS 的。
两边的符号名不同。加 `-mstack-protector-guard=tls` 即可。

### 6.2 `cannot find crt1.o`

见 §3.3。ARM GNU Toolchain 的 sysroot 在 `libc/` 子目录。

### 6.3 静态库里"自注册"失效

```cpp
// 看着没问题，实际可能根本不执行
struct Registrar { Registrar() { register_backend("x", make_x); } };
const Registrar g_registrar;
```

静态库链接时，如果某个 `.o` 里没有任何被引用的符号，链接器会**整个丢掉**，
静态对象自然不会构造。日志看起来就是"后端没注册"。

本项目改成显式调用：

```cpp
void ensure_builtin_backends() {
    static std::once_flag flag;
    std::call_once(flag, [] {
        detail::register_stub_backend();
#if defined(MYLIB_HAVE_ONNXRUNTIME)
        detail::register_onnxruntime_backend();
#endif
    });
}
```

### 6.4 `-DXXX="0.1.0"` 在 gcc 上被吃掉引号

CMake 在 Windows 上对命令行的引号转义，Ninja 和 MSVC 处理方式不同。
gcc 收到的是 `-DMYLIB_VERSION_STR=0.1.0`，于是报 `too many decimal points in number`。

解决：改用 `configure_file` 生成头文件（`src/core/build_info_config.h.in`）。
**这是跨平台工程里的通用建议：字符串宏一律用生成头，不要走命令行。**

### 6.5 `format()` 重载歧义

```cpp
namespace my::log {
template <class... Args> std::string format(fmt::format_string<Args...>, Args&&...);
template <class... Args> void info(fmt::format_string<Args...> f, Args&&... a) {
    write(Level::Info, format(f, a...));   // 编译错误：ambiguous
}
}
```

参数里有 `fmt::format_string`，ADL 会把 `fmt::format` 拉进候选集。写成 `::my::log::format(...)`。

### 6.6 `add_library(deps::spdlog ALIAS spdlog::spdlog)` 报错

CMake 不允许给 ALIAS 目标再起别名。套一层：

```cmake
add_library(deps_spdlog INTERFACE)
target_link_libraries(deps_spdlog INTERFACE spdlog::spdlog)
add_library(deps::spdlog ALIAS deps_spdlog)
```

### 6.7 不要用 INTERFACE 编译定义改三方库行为

曾经给 `deps::json` 加过 `JSON_USE_IMPLICIT_CONVERSIONS=0`，
结果所有消费方（包括演示"原生 API 怎么写"的示例）都编不过了。

**规则**：三方库的默认行为不要动；要改就在自己的 `src/` 里改。

## 7. 在自己的工程里使用

### 方式 A：源码嵌入（推荐）

```cmake
# 第三方库放在自己的 third_party/ 下（git submodule 最省事）
add_subdirectory(third_party/my_cpp_libs my_cpp_libs_build)

# 只链接真正用到的组件
target_link_libraries(app PRIVATE
    my_cpp_libs::log
    my_cpp_libs::json)
```

作为子目录嵌进宿主工程时，`my_cpp_libs` 会自动：

- 关闭示例 / 测试 / 工具（靠 `MYLIB_IS_TOP_LEVEL` 检测，不用手工关）；
- **不生成安装规则**（避免把本库的头文件和静态库塞进宿主工程的 install 前缀；
  需要时装 `-DMYLIB_INSTALL=ON`）；
- 构建产物写进 `my_cpp_libs_build/`（不再写到宿主工程的根目录）；
- 宿主工程如果已经自带 `spdlog` target，直接复用，不会重复 `add_subdirectory` 撞目标名。

只开需要的组件（可选，能明显缩短构建时间）：

```cmake
set(MYLIB_ENABLE_INFER OFF CACHE BOOL "")
set(MYLIB_ENABLE_CV    OFF CACHE BOOL "")
set(MYLIB_ENABLE_HTTP  OFF CACHE BOOL "")
add_subdirectory(third_party/my_cpp_libs my_cpp_libs_build)
```

完整可运行示例：[examples/consumer_app/](../examples/consumer_app/CMakeLists.txt)
—— 它链接 `log/json/math/net` 四个组件，真的跑一遍 JSON 往返、线性求解和 TCP 回环收发，
任何一步失败返回非 0，CI 会执行它（见 §4.3）。

```powershell
cmake -S examples/consumer_app -B build/consumer_app -G Ninja
cmake --build build/consumer_app
./build/consumer_app/consumer_app
```

优点：跟着你的工具链编，天然 ABI 一致；可以按需裁剪组件。

注意事项：

- 第一次 configure 会把 `resources/*.zip` 解压到 **my_cpp_libs/third_party**（不是宿主工程），
  离线环境要先把 zip 放好（`scripts/fetch-deps.ps1` / `fetch-deps.sh`）；
- **`-fno-exceptions` 只覆盖 core/math/dsp/net**：宿主若全局开 `-fno-exceptions`，
  log/json/http 编不过（[07 §5](07-图像链路与无异常构建.md)）；
- **共享库暂不支持**：`-DMYLIB_BUILD_SHARED=ON` 会直接报错，原因见 §9；
- 组件是**按需链接**的：只链 `my_cpp_libs::all` 会把 ORT/OpenCV 这些重依赖一起拖进来，
  板端工程尽量只链自己用到的（比如 `my_cpp_libs::image` 不需要 OpenCV）。

### 方式 B：安装成 SDK（二进制分发，`find_package`）

```bash
cmake -S . -B build/sdk -DMYLIB_INSTALL=ON
cmake --install build/sdk --prefix D:/sdk/my_cpp_libs
```

安装目录是**自包含**的：组件头 + 静态库 + 公共头需要的三方头（`nlohmann/`、`Eigen/`、
`spdlog/`）+ spdlog 静态库；启用 ORT/OpenCV 时还会带上它们的 `.so`/`.dll` 和 import lib。
消费方：

```cmake
find_package(my_cpp_libs CONFIG REQUIRED)
target_link_libraries(app PRIVATE my_cpp_libs::all)          # 或按组件挑
# my_cpp_libs::log / ::json / ::math / ::infer / ::cv ...
my_cpp_libs_copy_runtime_dlls(app)                            # 仅 Windows：拷 ORT/OpenCV DLL
```

注意事项：

- 需要 CMake ≥ 3.20；
- **交叉编译的消费方**要加 `-DCMAKE_PREFIX_PATH=<sdk>`；aarch64 工具链已把
  `CMAKE_FIND_ROOT_PATH_MODE_PACKAGE` 设成 `BOTH`，否则 SDK 不在 sysroot 里会找不到；
- Linux 下 ORT/OpenCV 的 `.so` 装在 `<sdk>/lib`，运行时要 `LD_LIBRARY_PATH` 指过去
  （或者拷到可执行文件旁边）；
- Windows 下 MSVC 必须 `/utf-8`（公共头里有中文）——SDK 的 `my_cpp_libs::platform`
  已经自动带上 `/utf-8`、`/Zc:__cplusplus`、`NOMINMAX`。

已发布的包（`dist/`，均可直接拷走）：

| 包 | 工具链 | ORT / OpenCV |
|---|---|---|
| `...-win-x64-msvc.zip` | MSVC | 1.23.2 / 4.12 |
| `...-linux-armv7-glibc230.tar.gz` | PetaLinux 2020.2 SDK | 1.18.1 / 4.12 |
| `...-linux-aarch64.tar.gz` | ARM GNU 14.2 | 1.19.2 / 4.12 |
| `...-win-x64-mingw-basic.zip` | MinGW | 无（MinGW 不用 MSVC ABI 的 ORT/OpenCV） |

> 已验证：MinGW（无 ORT/OpenCV）、MSVC + ORT 1.23.2 + OpenCV 4.12、aarch64 交叉
> （ORT 1.19.2 + OpenCV 4.12，产物在 Pi 4B 上跑通）各用一个独立工程 `find_package` 验证过。

### 版本管理

作为 git submodule（或 vendor 目录）固定版本：

```bash
git submodule add <url> third_party/my_cpp_libs
git -C third_party/my_cpp_libs checkout <tag 或 commit>
```

升级时只改 submodule 指针，宿主工程的 `CMakeLists.txt` 一行都不用动。

## 8. 常用选项

| 选项 | 默认 | 说明 |
|---|---|---|
| `MYLIB_INSTALL` | 顶层工程 ON | 生成安装规则；作为子目录嵌入时默认 OFF（避免污染宿主工程的安装前缀） |
| `MYLIB_BUILD_EXAMPLES` | 顶层工程 ON | 构建示例 |
| `MYLIB_BUILD_TOOLS` | 顶层工程 ON | 构建命令行工具（`model_inspect`） |
| `MYLIB_ENABLE_CORE` | ON | 核心组件（`Status`/`Result`/平台信息）；**不可关闭**：置 OFF 会 FATAL_ERROR（所有组件都依赖它） |
| `MYLIB_ENABLE_IO` | ON | 文件/目录/路径/临时文件（`std::filesystem` + **原子写**）；可用 `-fno-exceptions` |
| `MYLIB_ENABLE_TIME` | ON | 单调时钟/UTC 时间戳/计时器；可用 `-fno-exceptions` |
| `MYLIB_ENABLE_THREAD` | ON | 线程池/阻塞队列/周期任务；**不能**进 `-fno-exceptions` 子集（`std::thread` 靠异常上报） |
| `MYLIB_ENABLE_ONNXRUNTIME` | ON | 接入 ONNX Runtime 后端（`MYLIB_ENABLE_INFER` 开着时生效） |
| `MYLIB_BUILD_TESTS` | 顶层工程 ON | 构建单元测试 |
| `MYLIB_ENABLE_LOG` | ON | spdlog 组件 |
| `MYLIB_ENABLE_JSON` | ON | nlohmann 组件 |
| `MYLIB_ENABLE_MATH` | ON | Eigen 组件 |
| `MYLIB_ENABLE_INFER` | ON | 推理组件（无 ORT 时用 stub） |
| `MYLIB_ENABLE_NCNN` | OFF | 接入 ncnn 备选后端 |
| `MYLIB_ENABLE_IMAGE` | ON | 图像组件（stb 解码/缩放/预处理，不依赖 OpenCV） |
| `MYLIB_ENABLE_DSP` | ON | 信号处理组件（pocketfft；频谱/滤波/检测/识别/解调） |
| `MYLIB_ENABLE_ML` | ON | 机器学习组件（sklearn→ONNX 表格模型推理；依赖 infer + json） |
| `MYLIB_ENABLE_NET` | ON | 网络组件（TCP/UDP，裸 socket 封装） |
| `MYLIB_ENABLE_HTTP` | ON | HTTP 组件（cpp-httplib；依赖 json，需要 httplib-*.zip） |
| `MYLIB_HTTP_THREAD_POOL` | 4 | HTTP 服务端线程池大小（板端建议 2） |
| `MYLIB_ENABLE_CV` | OFF | 图像组件（需要 OpenCV） |
| `MYLIB_NO_EXCEPTIONS` | OFF | 以 `-fno-exceptions` 编译；**只支持 core + math + dsp + net**，其余组件开着会 FATAL_ERROR |
| `MYLIB_NCNN_ROOT` | 自动搜索 | ncnn 安装根目录 |
| `MYLIB_OPENCV_ROOT` | 自动搜索 | OpenCV 的 `OpenCV_DIR`（含 OpenCVConfig.cmake 的目录） |
| `MYLIB_BUILD_SHARED` | OFF | **暂不支持**：置 ON 会直接 FATAL_ERROR（公共头里50+ 个符号没标 `MYLIB_API`，见 §9） |
| `MYLIB_ONNXRUNTIME_ROOT` | 自动搜索 | ONNX Runtime 包根目录；**只作为用户覆盖入口**，自动探测结果不回写它 |
| `MYLIB_SANITIZE` | 空 | `address` / `undefined`（UBSan 走 trap 模式，不需要 libubsan）/ `thread`（TSan，抓数据竞争） |
| `MYLIB_DEPS_DIR` | `third_party` | 解压目标目录 |
| `MYLIB_AUTO_EXTRACT_DEPS` | ON | 自动解压 |

> 依赖选择是**每次 configure 重新探测**的（`third_party/onnxruntime-*` 按名字排序 + 架构校验），
> 不再把上次的结果写回 cache —— 否则"新放进去的包永远选不上"，同一份源码在新旧构建目录里
> 会链到不同版本的 ORT。configure 摘要里的 `ONNX Runtime :` 那一行就是最终选中的包名。

例：Zynq 上只要日志，把体积压到最小：

```powershell
cmake --preset linux-armv7 `
  -DMYLIB_ENABLE_JSON=OFF -DMYLIB_ENABLE_MATH=OFF -DMYLIB_ENABLE_INFER=OFF `
  -DMYLIB_BUILD_EXAMPLES=OFF -DMYLIB_BUILD_TESTS=OFF
```

## 9. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| configure 卡在 `Performing Test ...` | 交叉编译的 `try_compile` 需要实际调编译器 | 正常，首次会慢几秒 |
| `ninja: error: loading 'build.ninja'` | configure 失败导致没有生成 | 先看 configure 的报错 |
| 找不到 `cl.exe` | 用的是 Ninja + MSVC 但没进 VS 环境 | 用 `win-msvc` 预设（VS 生成器）或先 `vcvars64.bat` |
| `spdlog` 重复定义 | 你的工程里还链接了另一份 spdlog | 用 `SPDLOG_HEADER_ONLY` 或统一用本项目的 `deps::spdlog` |
| 修改 CMake 后行为没变 | 缓存里还是旧值 | 删掉 `build/<preset>` 重来 |
| 交叉编译的单测没法跑 | 目标机架构不同 | 正常，交叉编译时只构建不注册 CTest |
| 上板报 `GLIBC_2.38 not found` | 用了 `linux-armv7`（2024 SDK，glibc 2.39）的动态产物 | 改用 `linux-armv7-static` 或 `linux-armv7-sdk2020`，见 §3.2 |

### 已知问题

- **共享库暂不支持（选项已改成 fail-closed）**：`-DMYLIB_BUILD_SHARED=ON` 现在会直接
  `FATAL_ERROR`。原因：动态库构建开了 hidden visibility，但公共头里还有 50+ 个对外符号
  没标 `MYLIB_API`（`BuildInfo` 全套、`infer::Shape/Tensor`、`preprocess` 的后处理、
  `json::parse_file/save_file`、`image::load/save/prepare`、net/http 的移动构造等），
  消费方链接会报 undefined。默认的静态构建不受影响，也是推荐的交付形态。
  真要做动态库时：补全 `MYLIB_API` → 加 `VERSION/SOVERSION` → Windows 运行时 DLL 拷贝 →
  `install(EXPORT)` + config 文件 → CI 加 shared 链接测试。
- **presets 里写死了本机路径**（`D:/ProgramFiles/...`、`D:/ProgramData/...`），
  换机器需要改预设，或直接在 `CMakeUserPresets.json`（已 gitignore）里覆盖。
  CI 就是绕开预设直接给 `-D` 参数的。
