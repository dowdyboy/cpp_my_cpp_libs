## 1. 需求拆解

你的原始诉求可以拆成四条，后面所有设计都对着这四条来：

| # | 诉求 | 落地方式 |
|---|---|---|
| R1 | 作为 `resources/` 里那些库的**调用演示**，重点是常用 API | `examples/01~09` + `10_net_demo` / `11_http_api` 是封装层用法；`examples/10_native_*~14_native_ncnn` 是**原生 API 速查** |
| R2 | 输出一个包装库 `my_cpp_libs`，统一常用功能的 API | `include/my_cpp_libs/` + `src/`，按组件切成独立 target |
| R3 | 供自己其他工程复用（可能 x86、可能 ARM） | 源码分发 + `add_subdirectory`，见 `examples/consumer_app` |
| R4 | 跨 Windows / Linux、跨 x86 / ARM（Zynq） | 10 个 CMake configure 预设 + 6 个交叉工具链文件，同一份源码 |

一个隐含的第五条，我认为是最重要的：

> **R5：不要为了"统一"而发明第二套标准库。**
> 封装的收益必须来自"消除了重复劳动 / 消除了易错点"，否则就是在制造维护负担。

## 2. 现状盘点

### 2.1 resources 里的六个库

| 库 | 版本 | 形态 | 跨平台性 | 封装价值 | 结论 |
|---|---|---|---|---|---|
| Eigen | 5.0.0 | 纯头文件 | ★★★★★ 无平台假设 | 中：类型别名、姿态约定统一、错误路径 | 值得包 |
| nlohmann/json | 3.12.0 | 纯头文件 | ★★★★★ | 高：异常→Status、路径访问 | 值得包 |
| spdlog | 1.17.0 | 源码+CMake | ★★★★☆ 全平台 | 高：初始化模板化、自定义 sink、未初始化兜底 | 最值得包 |
| stb_image | 2.32 | 纯头文件（两个 .h） | ★★★★★ 无线程/系统假设 | 高：它补的是"板端没有 OpenCV 时怎么解码"这个洞 | 后加的，见 [07](07-图像链路与无异常构建.md) |
| pocketfft | 4d865cb | 纯头文件（单个 .h） | ★★★★★ | 高：FFT 是整个信号链路的底座，自己做不了 | 后加的，见 [08](08-信号处理与解调.md) |
| cpp-httplib | 0.66 | 纯头文件（单个 .h） | ★★★★☆ | 高：HTTP/1.1 的 keep-alive/分块/超时自己写一定错 | 后加的，见 [10](10-网络与HTTP.md) |

| ONNX Runtime | 1.23.2（Win x64）/ **1.18.1（板端 armv7）** | Windows x64 预编译；armv7 自编 | ★★☆☆☆ | 最高：它本身就是平台绑定的 | 必包，且必须做后端抽象 |
> ml 组件没有新增 C++ 依赖：sklearn 模型用 skl2onnx 在 **Python 侧**（conda t2xpu）导出成 ONNX，板端走已有的 ORT 后端。Python 侧需要 scikit-learn / skl2onnx / onnx，见 [09](09-机器学习模型集成.md)。

**ONNX Runtime 是唯一的风险点**，理由具体：

- 官方发布页只提供 `windows-x64 / windows-arm64 / linux-x64 / linux-aarch64 / macOS` 的预编译包；
- 没有 `linux-armv7`（Zynq-7000 是 Cortex-A9 = armv7-A）的官方产物；
- 你手上的 zip 是 **MSVC 编译的 DLL + .lib**，MinGW 虽然在链接层面往往能过，
  但跨 CRT 的 `std::string` 传递是未定义行为，不能作为正式方案。

所以架构上不能假设"推理一定存在"，必须能降级。这一点直接决定了 `infer` 组件的设计（见 §4.4）。

## 3. 可行性结论

### 3.1 判定

| 维度 | 判定 | 依据 |
|---|---|---|
| 技术可行性 | **高** | 5 个平台已全部编译链接通过，同一份源码零 `#ifdef` 业务代码 |
| 工程可行性 | **高** | 增量式：每个组件独立、可单独关闭，失败不影响其他部分 |
| 维护成本 | **中** | 三个头文件型库几乎零维护；ONNX Runtime 需要跟版本 |
| 主要风险 | **低** | ORT 的 ARM 支持已打通；剩余风险是板端实时性（2026-11-16 已上板实测通过） |

### 3.3 已踩平的坑（都是真坑，结论已固化进工程）

| 现象 | 根因 | 解法（已落地） |
|---|---|---|
| `undefined reference to __stack_chk_guard` | Ubuntu 的 gcc9 sysroot 默认 TLS 栈保护，与交叉 gcc 默认不一致 | toolchain 里加 `-mstack-protector-guard=tls -fno-pie -no-pie` |
| `cannot find crt1.o` | ARM GNU Toolchain 把 glibc sysroot 放在 `<prefix>/libc`，不是 `<prefix>` | toolchain 里显式指向 `.../aarch64-none-linux-gnu/libc` |
| `undefined reference to pthread_key_create`（ncnn 后端） | ncnn 静态库用 `pthread_key_*`，`deps::ncnn` 只在 Windows 上加了 `ws2_32`，Linux 侧没带 `-lpthread`；只链 `deps::ncnn` 的 target（原生 API 示例）就炸 | `deps::ncnn` 在非 Windows 上挂 `Threads::Threads` + `${CMAKE_DL_LIBS}` |
| Windows 上把 armv7 的 OpenCV 装进 `third_party/` 后 configure 失败（`IMPORTED_IMPLIB not set`） | Windows 分支的 glob 会匹配到 ELF 安装树，`find_package(CONFIG)` 又把 Linux `.so` 当导入库 | Windows 分支先过滤"含 `lib/libopencv_core.so` 的目录"，再走 `find_package` |
| SDK 的 `environment-setup` 在 `set -u` 下静默失败 | 环境脚本里有未定义变量引用；配合 `set -e` 导致构建脚本一行日志都没有就退出 | 构建脚本里 `set +u` 再 source、失败不致命（工具链文件里有 HINTS 兜底） |
| 后端"注册了但找不到" | 静态库里只有静态注册对象的 `.o` 会被链接器整个丢弃 | 改成 `detail::register_xxx()` 显式调用 + `std::call_once` |
| `-DMYVAR="0.1.0"` 在 gcc 上变 `0.1.0` | Windows 下不同生成器对命令行引号转义不一致 | 改用 `configure_file` 生成 `build_info_config.h` |
| `format(...)` 重载歧义 | ADL 把 `fmt::format` 一起拉进来了 | 调用处写成 `::my::log::format(...)` 全限定 |
| `add_library(deps::spdlog ALIAS spdlog::spdlog)` 报错 | CMake 不允许给 ALIAS 再起别名 | 套一层 `INTERFACE` 库再起别名 |
| 给三方库加 `JSON_USE_IMPLICIT_CONVERSIONS=0` 后用户代码编译不过 | 用 `INTERFACE` 编译定义改三方库行为会污染所有消费方 | 不要动三方库的默认行为，自定义逻辑放在自己的 `src/` |
| 4 通道丢 alpha 时顺手用了 `BGRA2BGR` | 缓冲区颜色顺序被悄悄改成 BGR，下游再按 `src_order` 交换一次 → **双重交换**，R/B 又反了 | 丢 alpha 只能用 `BGRA2BGR`/`RGBA2RGB` 这类**不改顺序**的转换；顺序的解释权只留给 `image_to_tensor(src_order, dst_order)` |
| 组件关掉后示例编崩（`mylib_log` 不是 target） | CMake 把不存在的 target 当普通库名放过，编译期才死在 `format.hpp` 的 spdlog 头 | 示例的守卫要写成 `TARGET mylib_log AND TARGET ...`，不能只判一个 |

这些坑的详细复现与解释在 [构建与交叉编译](03-构建与交叉编译.md)。

### 3.5 0.1.1 修复轮（2026-11-17）

一次全量评估（构建全绿、158 用例全过）之后又挖出一批**只在特定配置下才暴露**的缺陷，
其中三个的共性是"Release 下侥幸正确、Debug/ASan 下必崩"：

| 缺陷 | 为什么一直没被发现 |
|---|---|
| `least_squares()` 把矩阵喂给 `Eigen::Ref<VecXd>` | 所有 CI job 都是 Release 家族（`NDEBUG`），Eigen 断言从未执行 |
| `CHECK_NEAR` 对 NaN 恒通过 | 断言本身写错了，测试框架没有自测 |
| handler 里 `Server::stop()` 死锁 | 没有并发用例，也没有 TSan job |

完整清单与修法见 [CHANGELOG](../CHANGELOG.md)，原则总结成三条：

1. **必须有一个 Debug 构建**（`linux-debug`）：断言/前置条件检查不是"额外保险"，是唯一的检查；
2. **测试框架本身要有测试**（`tests/test_framework_self.cpp`）：框架出错会让所有用例一起说谎；
3. **声明线程安全就必须有并发用例**（`linux-tsan`）：否则只是把数据竞争复制到更多核上。

### 3.4 已修正的正确性缺陷（"跑得通、结果错、不报错"那一类）

| 缺陷 | 为什么会踩 | 修法与回归 |
|---|---|---|
| `float_to_half` 次正规分支右移 32~37 位（**UB**），`7.3e-12` 会变成 `1e-5` 量级 | `>> (shift+13)` 的移位量没设上界；x86 的 `shr` 按 32 取模，把尾数低位当结果 | 重写：先给 `<= 2^-25` 与上溢两个快路径，次正规分支移位量恒 < 32；加 3.4 万条位精确用例 + 一条独立参考实现的抽样比对 |
| 舍入是"第 12 位为 1 就进位"，不是 IEEE 的 RNE | 手写实现的常见偷懒 | 正规数用 `(m + 0x0FFF + lsb) >> 13`，次正规数同样带 RNE；跨后端比对 fp16 不再差 1 ULP |
| 次正规数进位到最小正规数时被 `& 0x3FF` 掩成 0 | `k` 可以是 1024 | 显式判 `k >= 0x400 -> 0x0400`（**这条是抽样比对时抓出来的**） |
| `image_to_tensor` 放行 4 通道但只写 3 个平面 | NHWC 下步长 3 与 4 不一致 → 数值整体错位 | 4 通道丢弃 alpha、输出 3 通道，并补 BGRA/RGBA 两个用例 |
| `normalize()` 忽略 layout，按 `i % 3` 取通道参数 | 对 NCHW 数据等于把均值按像素轮转 | 签名改成 `normalize(src, pixels, channels, spec, out)`，按 layout 算通道 |
| `keep_aspect=false` 时 letterbox 只有一个 `scale`，逆变换数学上不可能对 | 拉伸的 x/y 比例不同 | `Letterbox` 加 `scale_x/scale_y`，`unletterbox_box` 分别除；补 cv 端到端用例 |
| `log::shutdown()` 调 `spdlog::shutdown()`（进程级副作用），`init()` 先拆后建 | 二次 init 失败会把老配置一起拆掉；还会清空宿主自己的 logger | 只回收本库持有的 logger + 自建线程池；改成"先建成功再替换"；补两个用例 |
| armv7 预设名不副实：写着 Cortex-A9，实际 glibc 2.39 | 编译通过 ≠ 能部署 | 拆成 `linux-armv7` / `-static` / `-sdk2020` 三个预设，描述写清各自的 glibc 要求 |
| ORT 依赖选择被 `CACHE ... FORCE` 锁死 | 同一 preset、同一源码，新旧构建目录链不同版本的 ORT | 探测结果不再回写 cache；每次 configure 重新按"用户覆盖 → 目录名排序 + ELF 架构校验"选 |
| `cv::prepare` 无条件把图转成 3 通道 BGR | 灰度模型（工业检测很常见）根本喂不进去；4 通道固定按 BGRA 处理，RGBA 输入会 R/B 互换 | 加 `input_channels`（0/1/3）；4 通道按 `norm.src_order` 区分 BGRA/RGBA；补 image 用例 |
| `mylib_cv` 无条件链 `mylib_infer` | `-DMYLIB_ENABLE_INFER=OFF -DMYLIB_ENABLE_CV=ON` 在 generate 阶段直接失败，P5"组件独立开关"在这一格是假的 | 拆出 `mylib_preprocess`，cv/image 只依赖它，infer 改成"有就链"；CI 最小配置加断言 |
| 文档承诺 `-fno-exceptions` 交付，但零构建选项验证 | 板端真开就编译失败（20 多处 try/catch），用户会以为"库支持" | 收窄到 core + math + dsp + net，加 `MYLIB_NO_EXCEPTIONS` + configure 校验 + CI job（[07 §5](07-图像链路与无异常构建.md)） |
| CI 的两个 Windows job 没有 fetch-deps | `resources/*.zip` 不进 git，configure 必然在 `[deps] Eigen 头文件缺失` 处 FATAL_ERROR | 两个 job 补缓存 + fetch 步骤；缓存 key 带上脚本哈希 |
| 板端没有任何解码能力 | `cv` 组件绑死 OpenCV，armv7 上编不出来 → 相机链路第一步就断 | 新增 `my::image`（stb），不依赖 OpenCV（[07](07-图像链路与无异常构建.md)） |
| stb 这类无 tag 依赖无法固定版本 | master 漂移后，不同时间 clone 的工程行为会不一致 | fetch 脚本按 commit pin + SHA256 校验，再打包成 resources/*.zip |
| `unwrap_phase` 拿"已修正的相位"做相邻差 | 修正一次之后每一步都再差 2π，瞬时频率整段报废（纯单音的 iff 被算成 0.54，分类成 FSK） | 改成用**原始**相位做差；用例固定"复指数 → 瞬时频率恒为 0" |
| FSK 解调拿"去均值后的瞬时频率"去和绝对 mark/space 比 | 频率被搬到 0 附近，判决全错（BER≈0.5） | 瞬时频率加 `remove_mean` 开关，解调用绝对频率；用例用 2-FSK 钉住 |
| BPSK 定时只靠相位相干度挑 | 相干度对"符号落在实轴"不敏感，定时错一个符号也判满分 → BER 固定 0.5 | 定时改用平均符号功率挑，相干度只管频偏符号；用例带 3 Hz 频偏 |
| 突发检测的粗边界比真实信号早最多一个窗 | 解调段带一截静音，符号定时被带偏（示例里 FSK BER 0.35） | 返回前用 16 点滑窗幅度把边界收到峰值 10% 处 |

## 4. 架构设计

### 4.1 分层

```
 ┌──────────────────────────────────────────────────────────────┐
 │  业务代码（你的其他工程 / examples/consumer_app）              │
 └───────────────────────────┬──────────────────────────────────┘
                             │  只依赖 my_cpp_libs::* 的公共头
 ┌───────────────────────────▼──────────────────────────────────┐
 │  my_cpp_libs                                                  │
 │   core log json math infer image dsp ml net http cv            │
 │   Status 分级   路径   姿态/线代 后端抽象 解码缩放 频谱/滤波 模型推理│
 │   Result 滚动  异常→S  统计    注册表   letterbox 检测/解调 双输出  │
 └───────────────────────────┬──────────────────────────────────┘
                             │  只在 src/*.cpp 里出现
 ┌───────────────────────────▼──────────────────────────────────┐
 │ spdlog nlohmann Eigen ONNX Runtime/ncnn stb pocketfft (skl2onnx)│
 └──────────────────────────────────────────────────────────────┘
```

关键：**三方库的头文件基本不进公共头**（例外见下），这样换库时只需改 `src/`。

| 组件 | 公共头是否引入三方头 | 原因 |
|---|---|---|
| core | 否 | — |
| log | 否（`log.hpp`）/ 是（`format.hpp`） | 格式化能力必须暴露 fmt，拆成独立头按需包含 |
| json | **是** | `get<T>()` 是模板，必须看到 nlohmann |
| math | **是** | 返回 Eigen 类型，必须看到 Eigen |
| image | **是**（`preprocess.hpp` 里的 `NormalizeSpec`/`Shape`） | 张量参数要复用 infer 的定义，否则两套结构体会互相转错；但**不引入 stb 头** |
| dsp | 否 | 只暴露 `float`/`std::complex<float>` 和本库的结构体，pocketfft 完全在 `src/` 里 |
| ml | 否 | 只暴露 `Meta`/`Prediction`；ONNX 走 infer，sidecar 用 json，业务代码看不到三方类型 |
| infer | 否 | 完全隔离 `Ort::*`，这也是能换后端的前提 |

### 4.2 五条设计原则

**P1. 源码分发，不做二进制分发。**
ABI 不一致在"C++ 静态库 + 预编译产物"这个组合里是无解的（MSVC/GCC 的 STL 布局、
`_GLIBCXX_USE_CXX11_ABI`、libstdc++ 版本、`-D_GLIBCXX_USE_CXX11_ABI=0`……）。
正确的做法不是去兼容 ABI，而是**每个平台各自从源码编一次**。
消费方一条 `add_subdirectory` 就够了，这正是本项目推荐且唯一验证过的用法。

**P2. 对外 API 不用异常；实现层只在 core/math/dsp/net 上支持 `-fno-exceptions`。**
"公共 API 一律 `Status` / `Result<T>`，三方库抛的异常在 `src/` 边界被翻译"——这一条不变。

但"整库能用 `-fno-exceptions` 编"这条**做不到**：json（nlohmann）、infer（ONNX Runtime）、
cv（OpenCV）的错误上报机制本身就是异常，关掉只能退化成 `abort()`，
等于把"错误可返回"变成"错误即崩溃"。所以承诺收窄成：
`-DMYLIB_NO_EXCEPTIONS=ON` 时只有 core + math + dsp + net 可编，其余组件必须在 configure 阶段关掉
（否则 FATAL_ERROR 并说明原因），CI 有专门 job 守住这三件事。
细节与真值表见 [07 §5](07-图像链路与无异常构建.md)。

**P3. 平台能力靠"后端"降级，不靠 `#ifdef` 渗透业务代码。**
`infer` 的定义是"能推理就推理，不能就明确报错"，业务代码里没有 `#ifdef ZYNQ`。

**P4. 保留逃生舱。**
`json::Document::raw()` 返回 `nlohmann::json&`，`log::write()` 接受任意字符串。
封装挡不住的高级用法要能"下去"，否则用户会绕开整个库。

**P5. 组件可独立开关。**
`-DMYLIB_ENABLE_MATH=OFF` 就完全不编译 Eigen 相关代码，产物里一个字节都不会有。
嵌入式上这一条直接决定了可用性（见 §6 的体积数据）。

### 4.3 core：统一错误模型

```cpp
my::Result<int> r = compute();
if (!r) { my::log::error("{}", r.status().to_string()); return; }
use(r.value());
```

- `Status`：`Errc` 枚举 + 文本，`to_string()` 形如 `io_error: 无法打开文件 xxx`；
- `Result<T>`：内部 `std::variant<T, Status>`，`value()` 违反前置条件时 `abort()`（编程错误就该炸），
  提供 `value_or / map / operator*`；
- `Errc` 刻意粗粒度（14 个），跨模块映射成本低。

**为什么不用 `std::expected`**：C++23，而基线是 C++17（gcc 9.3 是最老的编译器）。

### 4.4 infer：后端抽象是这套设计的核心

```cpp
class Session {                       // 业务代码只认这个
public:
    virtual const char* backend_name() const noexcept = 0;
    virtual const std::vector<Port>& inputs()  const noexcept = 0;
    virtual const std::vector<Port>& outputs() const noexcept = 0;
    virtual Status run(const std::vector<Feed>&, std::vector<Outcome>&) = 0;
};

auto s = my::infer::Options opt; opt.model_path = "m.onnx"; auto s = my::infer::create_session(opt);;   // 自动挑后端
```

设计要点：

1. **`Ort::*` 不出现在任何公共头**，因此 armv7 上可以不带 ORT 编译；
2. **后端注册表**：`register_backend("ncnn", factory)` 就能加新后端，业务代码零改动；
3. **自动降级**：有模型文件时按 `onnxruntime → ncnn → stub` 优先级挑；没有模型文件直接用 `stub`；
4. **`stub` 后端不是摆设**：它把输入原样回显，用来在没模型/没库的阶段先把
   "采集 → 预处理 → 推理 → 后处理"整条链跑通，也是 Zynq 上的兜底。

Zynq 上的三条真实路线（按推荐度）：

| 方案 | 成本 | 适用 |
|---|---|---|
| A. 板端换 ncnn（支持 armv7 NEON） | 中，需实现一个 backend | 推荐。ONNX→ncnn 有现成转换 |
| B. 交叉编译 ONNX Runtime for armv7 | 高（protobuf/abseil 交叉编译链） | 模型算子特殊、必须用 ORT 时 |
| C. x86 侧推理，板子只做采集 | 低 | 实时性要求不高的场合 |

> armv7 这一栏必须 `strip -g` 才有可比性：PetaLinux SDK 的 environment-setup 会
> export `-g`，所以刚编出来的 `.a` 都是带调试信息的（dsp 有 8 MB，strip 完 402 KB）。
> 板端部署前记得 `arm-xilinx-linux-gnueabi-strip --strip-unneeded`。

> 板端如果只要其中一两种，加 `STBI_ONLY_*` 还能再砍。要注意的是它会被整个链进
> 最终可执行文件（静态库按目标文件粒度链接，stb 是**单文件**），所以
> `-DMYLIB_ENABLE_IMAGE=OFF` 是二进制体积敏感场景下唯一彻底的裁剪手段。

| 示例 | armv7 | x86_64 |
|---|---|---|
| example_log | 568 KB | 669 KB |
| example_json | 732 KB | 867 KB |
| example_math | 683 KB | 821 KB |
| example_infer | 600 KB | 706 KB |

对 Zynq-7000（通常 512MB DDR、几十 MB rootfs）来说，
单个功能二进制的量级完全可接受；`strip` 后还能再降 30~50%。
按组件裁剪（只开 `log`）可以把体积压到 100KB 量级。

## 9. 怎么开始用（三步）

**第一步：在你的工程里引入**

```cmake
add_subdirectory(path/to/cpp_my_cpp_libs my_cpp_libs_build)
target_link_libraries(your_target PRIVATE
    my_cpp_libs::log
    my_cpp_libs::json)
```

**第二步：代码里换掉散落实现**

```cpp
#include <my_cpp_libs/log/format.hpp>
#include <my_cpp_libs/log/log.hpp>

my::log::Config cfg;
cfg.level     = my::log::Level::Debug;
cfg.file_path = "logs/app.log";
my::log::init(cfg);        // 之后直接 my::log::info("x={}", x)

auto doc = my::json::Document::parse_file("config.json");
int port = doc.value().get_or<int>("server.port", 8080);
```

**第三步：交叉编译到板子**

```powershell
cmake --preset linux-armv7
cmake --build --preset linux-armv7
# 产物：build/linux-armv7/bin/your_app（ELF 32-bit ARM, EABI5, hard-float）
```

## 10. 几个明确的设计取舍（供后续复查）

| 决策 | 选择 | 放弃的方案 | 理由 |
|---|---|---|---|
| C++ 标准 | C++17 | C++20 / 23 | gcc 9.3 是工具链下限 |
| 依赖获取 | 本地 zip（离线） | FetchContent 联网 / vcpkg / Conan | 你的场景是固定版本 + 内网；零网络依赖最稳 |
| 库形态 | 静态库 | 动态库 | 板端部署简单；共享库选项已改为 fail-closed：`MYLIB_BUILD_SHARED=ON` 在 configure 阶段直接 FATAL_ERROR |
| ORT 引入方式 | 预编译包 + 后端抽象 | 一律源码编译 | 源码编译在 armv7 上成本过高，先用 abstract 隔离 |
| 错误处理 | Status/Result | 异常 / 错误码 int | 兼顾可移植性与可读性 |
| 测试框架 | 自研 100 行 | GoogleTest / Catch2 | 不增加依赖，交叉编译零负担 |
| 打包 | `find_package(my_cpp_libs CONFIG)` + 自包含三方依赖 | — | ✅ 已完成（已验证 MinGW / MSVC / aarch64） |
