# my_cpp_libs 规划与可行性评估

> 结论先行：**可行，而且已经跑通了**。本次交付的工程已经把 5 个目标平台全部编译链接通过，
> 69 个单元测试在 Windows(x64) 上全绿，并在 MSVC 下用真实 ONNX 模型完成了端到端推理。
> 唯一的硬约束是 ONNX Runtime 在 armv7（Zynq-7000）上没有官方二进制。
> 这一条已经解决：用 WSL + armhf 工具链交叉编译出了 `libonnxruntime.so`，
> 已接入 CMake 并完成链接与 ABI 版本核对（见 [04-推理方案](04-推理方案与模型兼容性.md)）。

## 1. 需求拆解

你的原始诉求可以拆成四条，后面所有设计都对着这四条来：

| # | 诉求 | 落地方式 |
|---|---|---|
| R1 | 作为 `resources/` 里那些库的**调用演示**，重点是常用 API | `examples/01~04` 是封装层用法；`examples/10~13` 是**原生 API 速查** |
| R2 | 输出一个包装库 `my_cpp_libs`，统一常用功能的 API | `include/my_cpp_libs/` + `src/`，按组件切成独立 target |
| R3 | 供自己其他工程复用（可能 x86、可能 ARM） | 源码分发 + `add_subdirectory`，见 `examples/consumer_app` |
| R4 | 跨 Windows / Linux、跨 x86 / ARM（Zynq） | 5 个 CMake 预设 + 3 个交叉工具链文件，同一份源码 |

一个隐含的第五条，我认为是最重要的：

> **R5：不要为了"统一"而发明第二套标准库。**
> 封装的收益必须来自"消除了重复劳动 / 消除了易错点"，否则就是在制造维护负担。

## 2. 现状盘点

### 2.1 resources 里的四个库

| 库 | 版本 | 形态 | 跨平台性 | 封装价值 | 结论 |
|---|---|---|---|---|---|
| Eigen | 5.0.0 | 纯头文件 | ★★★★★ 无平台假设 | 中：类型别名、姿态约定统一、错误路径 | 值得包 |
| nlohmann/json | 3.12.0 | 纯头文件 | ★★★★★ | 高：异常→Status、路径访问 | 值得包 |
| spdlog | 1.17.0 | 源码+CMake | ★★★★☆ 全平台 | 高：初始化模板化、自定义 sink、未初始化兜底 | 最值得包 |
| ONNX Runtime | 1.23.2 | **Windows x64 预编译**（MSVC ABI） | ★★☆☆☆ | 最高：它本身就是平台绑定的 | 必包，且必须做后端抽象 |

**ONNX Runtime 是唯一的风险点**，理由具体：

- 官方发布页只提供 `windows-x64 / windows-arm64 / linux-x64 / linux-aarch64 / macOS` 的预编译包；
- 没有 `linux-armv7`（Zynq-7000 是 Cortex-A9 = armv7-A）的官方产物；
- 你手上的 zip 是 **MSVC 编译的 DLL + .lib**，MinGW 虽然在链接层面往往能过，
  但跨 CRT 的 `std::string` 传递是未定义行为，不能作为正式方案。

所以架构上不能假设"推理一定存在"，必须能降级。这一点直接决定了 `infer` 组件的设计（见 §4.4）。

## 3. 可行性结论

### 3.1 判定

| 维度 | 判定 | 依据 |
|---|---|---|
| 技术可行性 | **高** | 5 个平台已全部编译链接通过，同一份源码零 `#ifdef` 业务代码 |
| 工程可行性 | **高** | 增量式：每个组件独立、可单独关闭，失败不影响其他部分 |
| 维护成本 | **中** | 三个头文件型库几乎零维护；ONNX Runtime 需要跟版本 |
| 主要风险 | **低** | ORT 的 ARM 支持已打通；剩余风险是上板实测 |

### 3.2 实测证据

```
目标           编译器        产物                     验证等级
win-msvc       MSVC 19.50     PE x64                  编译 ✅ 链接 ✅ 测试 ✅ 运行 ✅（含真实 ONNX 推理）
win-mingw      GCC 15.2       PE x64                  编译 ✅ 链接 ✅ 测试 ✅ 运行 ✅
linux-x64      GCC 9.3        ELF 64-bit x86-64       编译 ✅ 链接 ✅
linux-armv7    GCC 13.3       ELF 32-bit ARM EABI5 HF 编译 ✅ 链接 ✅
linux-aarch64  GCC 14.2       ELF 64-bit AArch64      编译 ✅ 链接 ✅
```

单元测试：69 个用例、0 失败（core 10 / log 6 / json 9 / math 13 / infer 10 / preprocess 15 / cv 6）。
另外在 WSL 下用 **ASan + UBSan 跑过一遍**（63 个用例，无任何内存/未定义行为报告，泄漏检测开启）。

**板端实测（Zynq-7020, Cortex-A9 @666MHz）**：63 个用例全绿；
MobileNetV2 量级的模型（224×224，≈300 MMAC）**549 ms/次**、峰值内存 140 MB，输出与 x86 逐位一致。
详见 [板端验证手册](06-板端验证手册.md)。

真实模型验证：官方模型库的 MobileNetV2-12 在 ORT 下正常（x86 单线程 13.9 ms/次），
但 `onnx2ncnn` 转换失败——见 [04](04-推理方案与模型兼容性.md) §6.3.1。

armv7 产物已确认是 `EABI5 + hard-float`（`e_flags & EF_ARM_ABI_FLOAT_HARD`），
可以直接在 Zynq-7000 的 PetaLinux 上跑。

### 3.3 已踩平的坑（都是真坑，结论已固化进工程）

| 现象 | 根因 | 解法（已落地） |
|---|---|---|
| `undefined reference to __stack_chk_guard` | Ubuntu 的 gcc9 sysroot 默认 TLS 栈保护，与交叉 gcc 默认不一致 | toolchain 里加 `-mstack-protector-guard=tls -fno-pie -no-pie` |
| `cannot find crt1.o` | ARM GNU Toolchain 把 glibc sysroot 放在 `<prefix>/libc`，不是 `<prefix>` | toolchain 里显式指向 `.../aarch64-none-linux-gnu/libc` |
| 后端"注册了但找不到" | 静态库里只有静态注册对象的 `.o` 会被链接器整个丢弃 | 改成 `detail::register_xxx()` 显式调用 + `std::call_once` |
| `-DMYVAR="0.1.0"` 在 gcc 上变 `0.1.0` | Windows 下不同生成器对命令行引号转义不一致 | 改用 `configure_file` 生成 `build_info_config.h` |
| `format(...)` 重载歧义 | ADL 把 `fmt::format` 一起拉进来了 | 调用处写成 `::my::log::format(...)` 全限定 |
| `add_library(deps::spdlog ALIAS spdlog::spdlog)` 报错 | CMake 不允许给 ALIAS 再起别名 | 套一层 `INTERFACE` 库再起别名 |
| 给三方库加 `JSON_USE_IMPLICIT_CONVERSIONS=0` 后用户代码编译不过 | 用 `INTERFACE` 编译定义改三方库行为会污染所有消费方 | 不要动三方库的默认行为，自定义逻辑放在自己的 `src/` |

这些坑的详细复现与解释在 [构建与交叉编译](03-构建与交叉编译.md)。

## 4. 架构设计

### 4.1 分层

```
 ┌──────────────────────────────────────────────────────────────┐
 │  业务代码（你的其他工程 / examples/consumer_app）              │
 └───────────────────────────┬──────────────────────────────────┘
                             │  只依赖 my_cpp_libs::* 的公共头
 ┌───────────────────────────▼──────────────────────────────────┐
 │  my_cpp_libs                                                  │
 │   core   log     json     math     infer                      │
 │   Status 分级    路径    姿态/线代  后端抽象                    │
 │   Result 滚动    异常→Status 统计   注册表                     │
 └───────────────────────────┬──────────────────────────────────┘
                             │  只在 src/*.cpp 里出现
 ┌───────────────────────────▼──────────────────────────────────┐
 │  spdlog   nlohmann/json   Eigen   ONNX Runtime / stub / ncnn  │
 └──────────────────────────────────────────────────────────────┘
```

关键：**三方库的头文件基本不进公共头**（例外见下），这样换库时只需改 `src/`。

| 组件 | 公共头是否引入三方头 | 原因 |
|---|---|---|
| core | 否 | — |
| log | 否（`log.hpp`）/ 是（`format.hpp`） | 格式化能力必须暴露 fmt，拆成独立头按需包含 |
| json | **是** | `get<T>()` 是模板，必须看到 nlohmann |
| math | **是** | 返回 Eigen 类型，必须看到 Eigen |
| infer | 否 | 完全隔离 `Ort::*`，这也是能换后端的前提 |

### 4.2 五条设计原则

**P1. 源码分发，不做二进制分发。**
ABI 不一致在"C++ 静态库 + 预编译产物"这个组合里是无解的（MSVC/GCC 的 STL 布局、
`_GLIBCXX_USE_CXX11_ABI`、libstdc++ 版本、`-D_GLIBCXX_USE_CXX11_ABI=0`……）。
正确的做法不是去兼容 ABI，而是**每个平台各自从源码编一次**。
消费方一条 `add_subdirectory` 就够了，这正是本项目推荐且唯一验证过的用法。

**P2. 对外 API 不用异常。**
Zynq 上常以 `-fno-exceptions` 交付；异常也让"错误必须处理"从签名上消失。
所以公共 API 一律 `Status` / `Result<T>`，三方库抛的异常在 `src/` 边界被翻译。

**P3. 平台能力靠"后端"降级，不靠 `#ifdef` 渗透业务代码。**
`infer` 的定义是"能推理就推理，不能就明确报错"，业务代码里没有 `#ifdef ZYNQ`。

**P4. 保留逃生舱。**
`json::Document::raw()` 返回 `nlohmann::json&`，`log::write()` 接受任意字符串。
封装挡不住的高级用法要能"下去"，否则用户会绕开整个库。

**P5. 组件可独立开关。**
`-DMYLIB_ENABLE_MATH=OFF` 就完全不编译 Eigen 相关代码，产物里一个字节都不会有。
嵌入式上这一条直接决定了可用性（见 §6 的体积数据）。

### 4.3 core：统一错误模型

```cpp
my::Result<int> r = compute();
if (!r) { my::log::error("{}", r.status().to_string()); return; }
use(r.value());
```

- `Status`：`Errc` 枚举 + 文本，`to_string()` 形如 `io_error: 无法打开文件 xxx`；
- `Result<T>`：内部 `std::variant<T, Status>`，`value()` 违反前置条件时 `abort()`（编程错误就该炸），
  提供 `value_or / map / operator*`；
- `Errc` 刻意粗粒度（14 个），跨模块映射成本低。

**为什么不用 `std::expected`**：C++23，而基线是 C++17（gcc 9.3 是最老的编译器）。

### 4.4 infer：后端抽象是这套设计的核心

```cpp
class Session {                       // 业务代码只认这个
public:
    virtual const char* backend_name() const noexcept = 0;
    virtual const std::vector<Port>& inputs()  const noexcept = 0;
    virtual const std::vector<Port>& outputs() const noexcept = 0;
    virtual Status run(const std::vector<Feed>&, std::vector<Outcome>&) = 0;
};

auto s = my::infer::create_session({.model_path = "m.onnx"});   // 自动挑后端
```

设计要点：

1. **`Ort::*` 不出现在任何公共头**，因此 armv7 上可以不带 ORT 编译；
2. **后端注册表**：`register_backend("ncnn", factory)` 就能加新后端，业务代码零改动；
3. **自动降级**：有模型文件时按 `onnxruntime → ncnn → stub` 优先级挑；没有模型文件直接用 `stub`；
4. **`stub` 后端不是摆设**：它把输入原样回显，用来在没模型/没库的阶段先把
   "采集 → 预处理 → 推理 → 后处理"整条链跑通，也是 Zynq 上的兜底。

Zynq 上的三条真实路线（按推荐度）：

| 方案 | 成本 | 适用 |
|---|---|---|
| A. 板端换 ncnn（支持 armv7 NEON） | 中，需实现一个 backend | 推荐。ONNX→ncnn 有现成转换 |
| B. 交叉编译 ONNX Runtime for armv7 | 高（protobuf/abseil 交叉编译链） | 模型算子特殊、必须用 ORT 时 |
| C. x86 侧推理，板子只做采集 | 低 | 实时性要求不高的场合 |

## 8. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| ORT 在 armv7 不可用 | ~~高~~ 已解决 | 中 | 已交叉编译出 armv7 版 `libonnxruntime.so` 并接入；仍保留 ncnn 作为备选后端 |
| 目标板 glibc 比 SDK 旧 | 中 | 高（运行时 `GLIBC_2.xx not found`） | 交叉编译时把 `MYLIB_TARGET_SYSROOT` 指向板子自己的 sysroot |

| 一次性铺太多组件 | 高 | 中 | 按 M1→M2 的节奏，一次一个 |

## 9. 怎么开始用（三步）

**第一步：在你的工程里引入**

```cmake
add_subdirectory(path/to/cpp_my_cpp_libs my_cpp_libs_build)
target_link_libraries(your_target PRIVATE
    my_cpp_libs::log
    my_cpp_libs::json)
```

**第二步：代码里换掉散落实现**

```cpp
#include <my_cpp_libs/log/format.hpp>
#include <my_cpp_libs/log/log.hpp>

my::log::Config cfg;
cfg.level     = my::log::Level::Debug;
cfg.file_path = "logs/app.log";
my::log::init(cfg);        // 之后直接 my::log::info("x={}", x)

auto doc = my::json::Document::parse_file("config.json");
int port = doc.value().get_or<int>("server.port", 8080);
```

**第三步：交叉编译到板子**

```powershell
cmake --preset linux-armv7
cmake --build --preset linux-armv7
# 产物：build/linux-armv7/bin/your_app（ELF 32-bit ARM, EABI5, hard-float）
```

## 10. 几个明确的设计取舍（供后续复查）

| 决策 | 选择 | 放弃的方案 | 理由 |
|---|---|---|---|
| C++ 标准 | C++17 | C++20 / 23 | gcc 9.3 是工具链下限 |
| 依赖获取 | 本地 zip（离线） | FetchContent 联网 / vcpkg / Conan | 你的场景是固定版本 + 内网；零网络依赖最稳 |
| 库形态 | 静态库 | 动态库 | 板端部署简单；共享库选项已保留但未验证 |
| ORT 引入方式 | 预编译包 + 后端抽象 | 一律源码编译 | 源码编译在 armv7 上成本过高，先用 abstract 隔离 |
| 错误处理 | Status/Result | 异常 / 错误码 int | 兼顾可移植性与可读性 |
| 测试框架 | 自研 100 行 | GoogleTest / Catch2 | 不增加依赖，交叉编译零负担 |
| 打包 | 先不做 | find_package | M4 再做，避免过早设计导出策略 |
