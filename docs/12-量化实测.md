# Int8 量化：从"性价比第一名"到可复现的数字

> 状态：**已完成实测**（2026-11-18，x86_64 / ONNX Runtime CPU EP）。
> 板端（Zynq-7020 / Cortex-A9）的数字**还没测**，原因见 §6 —— 那里也是这份文档最重要的部分。

[04 §8](04-推理方案与模型兼容性.md) 一直把 Int8 量化列为"性价比第一名"（2~3× 速度、1/4 体积），
但**一个数字都没有**。这一版把链路固化下来并给出了实测值，顺带纠正了三个容易踩的假设。

---

## 1. 结论先行

在 x86_64 上用**我们自己的 `my::infer`**（`model_inspect`）实测：

| 模型 | 输入 | fp32 | Int8 (QDQ) | 加速 | 体积 |
|---|---|---|---|---|---|
| `small_cnn` | 1×3×32×32 | 0.054 ms | 0.088 ms | **0.61×（更慢）** | 22 → 11 KB（2.03×）|
| `bench_cnn` | 1×3×224×224 | 6.83 ms | 5.03 ms | **1.36×** | 551 → 149 KB（3.69×）|
| `mobilenetv2-12` | 1×3×224×224 | 11.27 ms | 5.55 ms | **2.03×** | 13.6 MB → 3.7 MB（3.64×）|

三条结论：

1. **模型越大越值得量化**。MobileNetV2 拿到 2.03×，而 `bench_cnn` 只有 1.36×，
   32×32 的 `small_cnn` **反而更慢**（0.61×）—— Q/DQ 节点的额外开销超过了计算节省。
2. **体积收益是稳定的 ~2~3.7×**，与模型大小关系不大（小模型的权重占比更低）。
3. **精度必须用真实校准集验证**。用合成数据校准，MobileNet 的 top-1 一致率是 **0%**
   （详见 §4）—— 这不是量化器的错，是校准集不代表真实分布。

## 3. 量化参数怎么选的

```python
quantize_static(
    pre_path, qdq_path, reader,
    quant_format=QuantFormat.QDQ,     # 用 Q/DQ 而非 QOperator：ORT 后续演进只维护 QDQ
    per_channel=True,                 # 逐通道权重量化：卷积核各通道分布差异大，必须逐通道
    activation_type=QuantType.QUInt8, # 激活用无符号（ReLU 之后天然非负）
    weight_type=QuantType.QInt8,      # 权重有符号
)
```

固定 `QDQ + per_channel + QUInt8/QInt8` 的理由：

- **QDQ**：ORT 官方从 1.7 起推荐，且只有 QDQ 图能被后续版本持续优化；
  `QOperator` 格式在新版本里逐渐不再更新。
- **per-channel**：逐张量量化在深度可分离卷积（MobileNet 的主要结构）上掉点非常明显。
- **激活 QUInt8**：常见 CNN 的激活在 ReLU 后为 [0, +∞)，用无符号量化多出 1 bit 有效精度。

## 4. 精度：合成校准数据不够用（实测证据）

脚本默认用合成数据（均匀噪声 / 梯度 / 棋盘 / 正弦）做校准，这对**玩具模型**没问题：

| 模型 | max_abs | 平均绝对误差 | 余弦相似度（最差） | top-1 一致率 |
|---|---|---|---|---|
| `small_cnn` | 0.0036 | 0.00105 | 0.99996 | 100% |
| `bench_cnn` | 0.0006 | 0.00017 | 0.99986 | 100% |

但对**真实模型**就崩了：

| 校准数据 | 余弦相似度（最差） | top-1 一致率 |
|---|---|---|
| 均匀噪声 | 0.955 | 4/8 |
| 1/f 谱（近似自然图像统计） | 0.914 | 2/8 |
| 梯度+斑点 | 0.915 | 0/8 |
| **真实图片（应当使用）** | 未测（本机无图库） | — |

也就是说：合成校准让 MobileNetV2 的量化参数完全跑偏（top-1 0~50%），
**任何"用合成数据量化，精度看起来还行"的结论都是假的**。

> 结论：`--calib-dir` 不是可选项，是必选项。本机能做的只有把流程和速度跑通；
> 精度必须在你自己的业务数据集上重跑（`--calib-dir <图片目录> --calib 200`）。
> 这样得到的模型才可能上板。

## 5. 两个真实的坑

### 5.1 opset < 13 的模型量化出来是**非法图**

`QuantizeLinear` / `DequantizeLinear` 的 `axis` 属性是 **opset 13** 才引入的。
ORT 的量化器不看你模型的 opset，照样写出带 `axis` 的 Q/DQ 节点；
于是 opset 12 的模型（例如 ORT Model Zoo 的 `mobilenetv2-12`）量化后会加载失败：

```
INVALID_GRAPH ... Error Unrecognized attribute: axis for operator DequantizeLinear
```

更阴的是：**量化阶段不报错**，只在"加载量化后的模型"时才炸。
脚本里已经加了 `ensure_opset13()`：opset < 13 时先用 `onnx.version_converter` 升到 13
再量化（升完 opset 后数值不变，已验证 fp32 输出一致）。

### 5.2 动态量化对 CNN 不可用

`quantize_dynamic` 把 Conv 变成 `ConvInteger`，而 **ORT CPU EP 没有实现 ConvInteger**：

```
NOT_IMPLEMENTED : Could not find an implementation for ConvInteger(10) node with name 'conv0_quant'
```

官方文档也说明了：动态量化只适合 MatMul 为主的模型（RNN / Transformer）。
所以脚本默认只做静态量化，`--with-dynamic` 仅在非 CNN 才值得试。

## 6. 板端（Zynq-7020）的预期：别把 2~3× 当承诺

这是本文最需要强调的一点。**上面 2.03× 的数字来自 x86_64**，它有 AVX2/VNNI 这类
int8 点积指令；而：

| 平台 | int8 点积指令 | 预期 |
|---|---|---|
| x86_64 (AVX2/VNNI) | 有 | 实测 1.36~2.03× |
| ARMv8.2+ (SDOT/UDOT) | 有 | 量级类似 |
| **Cortex-A9 / ARMv7（Zynq-7020）** | **没有** | 收益主要来自带宽与指令数减少，可能只有 1.0~1.4×，**甚至可能更慢** |

A9 的 NEON 是 128-bit 但**没有 int8 乘加**，MLAS 在 armv7 上对 int8 是回退/较少优化路径；
再加上 Q/DQ 节点的额外搬运，`small_cnn` 上已经实测到 0.61× 的反例。
所以 [04 §8](04-推理方案与模型兼容性.md) 那个 "Zynq 上 2~3×" 的说法应当改成条件句：
**2~3× 隐含了 int8 点积指令的前提，ARMv7 上必须先测**。

上板验证怎么做（板子到位后）：

```bash
# 1) 把 qdq 模型拷到板子
scp models/int8/bench_cnn_qdq.onnx root@<board>:/tmp/
# 2) 用板端 model_inspect 测（注意板端 ORT 是 1.18.1）
/tmp/model_inspect /tmp/bench_cnn_qdq.onnx --run --bench 20
/tmp/model_inspect /tmp/bench_cnn.onnx      --run --bench 20
```

需要同时确认：板端 ORT 1.18.1 能加载 QDQ 图（`QuantizeLinear`/`DequantizeLinear` 在 1.18 支持，
但 armv7 的内核实现需要实测），以及 QDQ 节点是否被图优化折叠掉（否则等于白量化）。

## 7. 要不要量化：判断清单

| 情况 | 建议 |
|---|---|
| 模型 ≥ 20 MB，且目标平台是 x86/ARMv8 | **值得**，先按本流程跑一遍，精度用真实校准集验 |
| 模型 < 1 MB 或单次推理 < 0.2 ms | **不值得**（实测更慢），先看分辨率/模型结构 |
| 目标平台是 Cortex-A9 这类 ARMv7 | **必须先上板测**，别按 x86 数字做决策 |
| 拿不到有代表性的校准集 | **先别做**，合成校准的精度是不可信的（§4 实测） |
| 表格模型（`ai.onnx.ml` 的 TreeEnsemble） | 量化器会原样放过，本来就不适用 |
