# 基础组件：io / time / thread / 分层配置

> 这四个是 0.1.2 补的"工程底座"。**它们的共同点：不封装任何三方库**，
> 解决的是"每个工程都会重写一遍、而每次重写都会踩同一个坑"的那部分代码。
>
> 判断标准沿用 [规划 §4.2 的 R5](01-规划与可行性.md)：包装的收益必须来自
> **消除重复劳动 / 消除易错点**，否则就是在制造维护负担。这四个都过了这条线：
> 原子写、时区、线程生命周期、配置优先级，每一样都有"写错了但跑得通"的典型踩法。

| 组件 | target | 依赖 | `-fno-exceptions` 子集 | 一句话 |
|---|---|---|---|---|
| `my::io` | `my_cpp_libs::io` | `std::filesystem` | ✅ | 文件/目录/路径/临时文件，**原子写** |
| `my::time` | `my_cpp_libs::time` | `<chrono>` | ✅ | 单调时钟、时间戳格式化、`Stopwatch` |
| `my::thread` | `my_cpp_libs::thread` | `<thread>` | ❌（`std::thread` 构造靠异常上报） | 线程池、阻塞队列、周期任务 |
| `my::json::Layered` | 复用 `my_cpp_libs::json` | nlohmann | ❌（随 json） | 分层配置：默认值 ← 文件 ← 环境 ← 命令行 |

分层配置**没有**独立 target：它本质就是"JSON 的深合并"，独立组件只会多一层类型转换
（见 [规划 §5 P1](01-规划与可行性.md) 的建议）。

## 1. `my::io`

### 1.1 为什么不是"直接用 std::filesystem"

`std::filesystem` 有两套重载：抛异常的和带 `error_code` 的。工程里真正需要的是后一套，
但每次都要写 `std::error_code ec; fs::xxx(p, ec); if (ec) ...`，于是大多数人图省事用抛异常那套，
然后在一个 `noexcept` 函数里被 `bad_alloc`/`filesystem_error` 打成 terminate。

这一层做的事：

1. 统一成 `Status` / `Result<T>`，错误消息里带上路径和 `ec.message()`；
2. **`write_file` 是原子的**；
3. 路径运算（`join/parent/stem/extension`）单独提供，不必为了拼一个路径引入 `<filesystem>`。

### 1.2 原子写为什么重要

配置文件写到一半被 kill、板子突然掉电，`std::ofstream` 直接 truncate 原文件的结果是
**半个 JSON** —— 下次启动解析失败，而"上次写的是对的"这个信息永久丢失。

`write_file` 的做法：

```
1. 在**同一目录**写 <name>.<timestamp>-<counter>.tmp
2. flush
3. rename(tmp, target)                // POSIX：原子替换
   Windows：rename 不覆盖已存在文件 → 先 remove(target) 再 rename
```

同一目录很关键：跨文件系统的 rename 不是原子操作（会退化成"复制+删除"）。

> 已知取舍：Windows 分支那一小段"先删后改名"的窗口里如果掉电，结果是**没有文件**
> （不是半截文件）。这仍然比留下半截配置好，因为"文件不存在"可以被明确处理。

### 1.3 用法

```cpp
// 路径运算（纯字符串，不碰文件系统）
std::string p = my::io::join(dir, "config.json");
std::string ext = my::io::extension(p);          // ".json"

// 读写
if (auto st = my::io::read_file("config.json"); st) {
    my::log::info("配置 {} 字节", st.value().size());
} else if (st.status().code() == my::Errc::NotFound) {
    // 首次运行：没有配置文件是正常的
}

// 原子落盘
MYLIB_CHECK(my::io::write_file("out.json", doc.dump(2)));

// 临时文件（RAII，析构即删）
auto tmp = my::io::TempFile::create();          // 当前目录
(*tmp).write("half-baked");
std::string final_path = tmp.value().release();  // 交出去，不删
```

### 1.4 接口一览

| 分类 | 函数 |
|---|---|
| 查询 | `exists` / `is_directory` / `info` / `list_dir`（结果已排序） |
| 读写 | `read_file` / `write_file`（原子）/ `append_file` |
| 元操作 | `create_directories` / `remove` / `remove_all` / `rename` / `copy_file` / `file_size` |
| 路径 | `join` / `parent` / `filename` / `stem` / `extension` / `current_dir` / `absolute` |
| 临时文件 | `TempFile::create` / `write` / `append` / `release` / `reset` |

约定：

- `read_file` 对不存在的文件返回 `NotFound`（不是 `IoError`），因为"没配"和"配坏了"要能分开；
- `remove` 对不存在的路径返回 `NotFound`；`remove_all` 则**幂等**（不存在也算成功）；
- `write_file` **不会**自动创建父目录 —— 目录结构缺失是设计错误，不该被静默吞掉。

## 2. `my::time`

### 2.1 两条必须记住的约定

1. **测耗时只能用单调时钟**（`monotonic_us/s`、`Stopwatch`）。
   系统时钟会被 NTP/手动改时间跳变，用它测出来的耗时可能是负数。
2. **日志时间戳默认 UTC**（`format_utc` → `...Z`）。
   要本地时间显式调 `format_local`，否则同一份日志在不同时区读起来会打架。

### 2.2 用法

```cpp
// 测耗时
my::time::Stopwatch watch;
do_work();
my::log::info("耗时 {}", my::time::format_elapsed(watch.elapsed_s()));  // "1.234 s"

// 作用域计时（析构时回调，异常会被吞掉，不影响主流程）
{
    my::time::ScopedTimer timer([&](double s) { stats.record(s); });
    do_work();
}

// 时间戳
std::string ts = my::time::format_utc(my::time::unix_ms());  // "2026-11-18T03:16:22.123Z"
std::string local = my::time::format_local(my::time::unix_ms());  // "2026-11-18 11:16:22"
```

| 函数 | 说明 |
|---|---|
| `monotonic_us` / `monotonic_s` | 单调时钟（测耗时） |
| `unix_ms` | 墙上时钟（时间戳） |
| `format_utc(ms, with_ms=true)` | ISO-8601 UTC，`2026-11-18T03:16:22.123Z` |
| `format_local(ms, fmt)` | 本地时间，`strftime` 格式串；失败返回**空串**（不留半截） |
| `format_elapsed(s)` | `us / ms / s / m / h` 自适应，负数与 NaN 返回 `n/a` |
| `Stopwatch` | `reset` / `elapsed_s` / `elapsed_ms` / `elapsed_us` |
| `ScopedTimer` | 构造即开始，析构回调；`cancel()` 取消；回调异常被吞 |
| `sleep_ms` / `sleep_s` | 负值直接返回（避免实现定义的睡眠） |

> `format_local` 内部用 `localtime_r` / `localtime_s`，是线程安全的
> （`std::localtime` 不是）。

## 3. `my::thread`

### 3.1 为什么不用"裸 std::thread"

板端是双核 A9，"采集 + 推理 + HTTP"三个线程是常态。裸 `std::thread` 的四个坑：

1. 忘记 `join` → 析构时 `std::terminate`；
2. 条件变量忘记用谓词 → **虚假唤醒**导致逻辑错；
3. 队列无界 → 消费慢就吃满内存（板子只有 512 MB DDR）；
4. 在回调里 `stop()` 自己 → `join` 自己抛 `system_error` 或死锁。

这三类组件（池/队列/周期任务）把上面四条都封在里面。

### 3.2 用法

```cpp
// 线程池
auto pool = my::thread::ThreadPool::create(0);   // 0 = 按硬件并发度
MYLIB_CHECK(pool);
auto fut = pool.value()->submit([](int x) { return x * 2; }, 21);
int v = fut.get();                               // 42
pool.value()->shutdown(/*drain=*/true);          // 也可以省略：析构会 drain

// 有界阻塞队列（capacity 0 = 无界）
my::thread::BlockingQueue<Frame> q(64);
if (!q.push(std::move(frame))) { /* 已经 close() */ }
Frame out;
if (q.pop_timeout(out, std::chrono::milliseconds(100))) { process(out); }
q.close();                                       // 唤醒所有等待者

// 周期任务（心跳/采样）
auto task = my::thread::PeriodicTask::create(std::chrono::milliseconds(100), [&] {
    sample();
});
...
task.value()->stop();
```

### 3.3 契约（这条最容易踩）

| 行为 | 约定 |
|---|---|
| `ThreadPool` 析构 | drain 后 join，不会 terminate |
| `submit` 之后立刻 `shutdown(false)` | 未开始的任务被丢弃，`future.get()` 抛 `std::future_error(broken_promise)` |
| `PeriodicTask` 回调抛异常 | 被吞掉并计入 `errors()`，周期继续 |
| 在回调里调 `PeriodicTask::stop()` | 合法：只置标志、**不 join 自己**；由之后从别的线程来的 `stop()`/析构 join |
| 在回调里销毁 `PeriodicTask` | **不合法**（没有安全时机去 join），析构会退化成 detach |
| `PeriodicTask` 周期 | 固定速率；单次执行超时后直接对齐到 `now + period`，不会"追补式突发" |

> `my::thread` 不在 `-fno-exceptions` 子集里：`std::thread` 构造失败只能靠
> `std::system_error` 上报，关掉异常就只剩 abort（与"错误可返回"的契约冲突）。
> `io` 和 `time` 不在这个问题上 —— 它们全部走 `error_code` 与 `chrono`。

## 4. 分层配置 `my::json::Layered`

### 4.1 优先级

```
默认值（代码里）  <  文件（可多个）  <  环境变量  <  命令行
```

后加的覆盖先加的。合并规则：**对象递归深合并，数组与标量整体覆盖**。
数组不做逐元素合并 —— 否则"删掉一项"在配置里变成不可能。

### 4.2 用法

```cpp
my::json::Document defaults;
defaults.set("server.port", 8080);
defaults.set("server.host", "0.0.0.0");
defaults.set("worker.count", 2);

my::json::Layered cfg;
cfg.add_defaults(std::move(defaults));
MYLIB_CHECK(cfg.add_file_if_exists("config.json"));  // 不存在就跳过
MYLIB_CHECK(cfg.add_env("MYAPP"));                   // MYAPP__SERVER__PORT=9090
MYLIB_CHECK(cfg.add_argv(argc, argv));               // --server.port=9090

int port = cfg.value<int>("server.port", 8080);
cfg.layers();   // 每层的来源，排查"这个值到底谁设的"
```

### 4.3 环境变量与命令行的映射

| 输入 | 解析结果 |
|---|---|
| `MYAPP__SERVER__PORT=9090` | `{"server":{"port":9090}}`（值按 JSON 解析） |
| `MYAPP__SERVER__HOST=abc` | `{"server":{"host":"abc"}}`（非 JSON 当字符串） |
| `MYAPP__DEBUG=true` | `{"debug":true}` |
| `--server.port=9090` | `{"server":{"port":9090}}` |
| `--server.host 0.0.0.0` | `{"server":{"host":"0.0.0.0"}}`（下一个参数不以 `--` 开头时当值）|
| `--verbose` | `{"verbose":true}` |

非法路径（如 `--a..b=1`）**必须报错**，不能静默忽略 —— 配置写错了要当场看见。

### 4.4 落盘

`Document::save_file` 是直接 truncate 写的（历史行为，未改）。
新代码建议：

```cpp
MYLIB_CHECK(my::io::write_file("config.json", cfg.merged().dump(2)));
```

## 5. `my::hash`（SHA-256）

```cpp
#include "my_cpp_libs/core/hash.hpp"

const std::string hex = my::hash::sha256_hex("abc", 3);        // 一次性
auto file_hash = my::hash::sha256_file_hex("model.onnx");       // 分块读，不整文件进内存

my::hash::Sha256 h;                                             // 增量
h.update(buf, n);
h.update(more, n2);
std::string digest = h.hex_digest();                            // 64 字符小写，取完自动复位

if (!my::hash::digest_equal(actual, expected)) { /* 不匹配 */ }
```

**为什么自己写**：板端要校验"这个 .onnx / 固件 / 数据文件是不是我以为的那个"，需要的只是
一个哈希函数。引 OpenSSL 等于为 200 行代码拖进一个几 MB 的库，交叉编译还多一层坑。

| 接口 | 说明 |
|---|---|
| `sha256_hex(data, len)` / `sha256_hex(string_view)` | 一次性摘要（64 字符小写十六进制） |
| `sha256_file_hex(path)` | 文件摘要，16 KiB 分块读；打不开返回 `Status`（带路径与 errno） |
| `Sha256::update` / `digest` / `hex_digest` | 增量式计算；`digest()` 取完**自动复位**，可直接复用对象 |
| `digest_equal(a, b)` | **常数时间**比较，大小写不敏感 —— 比较来自外部的摘要不要用 `==` |

正确性由公开测试向量守着（NIST/FIPS 180-4）：空串 `e3b0c442…`、`"abc"` `ba7816bf…`、
两个块的串 `248d6a61…`、100 万个 `'a'` `cdc76e5c…`。另外测了"分段喂 vs 一次喂结果相同"
（63/64/65 这些块边界）、空文件、复用对象、文件路径不存在。

> 实测与 `Get-FileHash`（Windows 独立实现）对同一批模型文件结果一致 —— 交叉验证过一次。

**它已经用在哪**：`my::ml::Model::load()` 默认核对 sidecar 里记录的模型 sha256，
用于发现"模型被替换/截断/量化后忘了更新 sidecar"（见 [09](09-机器学习模型集成.md)）。

| MSVC x64 Release（ORT+ncnn+OpenCV） | 见 CHANGELOG（含 `--fail-on-skip`） |
| Linux Debug / ASan / TSan | 见 CHANGELOG |
| `-fno-exceptions`（core+math+dsp+net+io+time+serial） | 见 CHANGELOG |

`thread` 的用例同时是 TSan job 的主要食粮：并发写日志、线程池 200 任务、

必须被真正并发跑一遍的地方。

## 7. 还没做

- `io`：目录遍历的递归版本（`list_dir_recursive`）、文件锁（`flock`/`LockFileEx`）
  —— 等有跨进程写同一个文件的需求再加；
- `time`：ISO-8601 解析（目前只格式化，不解析）、时区名支持（只支持进程本地时区）；
- `thread`：任务优先级、`std::future` 之外的 `then` 链 —— 属于"用到了再说"；
- 配置：JSON Schema 校验、配置项热重载。
