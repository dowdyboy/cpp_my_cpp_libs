# 串口通信（`my::serial`）

> 适用场景：Zynq 上接 FPGA 命令通道、GPS/NMEA、Modbus RTU、传感器串口，
> 以及上位机连 USB 转串口。**不覆盖**：USB CDC 自定义协议栈、RS-485 方向控制引脚
> （需要更底层的 UART 驱动或 GPIO 配合）。

## 1. 为什么自己写而不是引库

| 方案 | 为什么不选 |
|---|---|
| Boost.Asio | 一个重依赖换来的是"异步 + 定时器"，而板端串口是"打开 → 配波特率 → 收发"；且 Zynq 上编译 Asio 的时间比整个库还长 |
| Qt `QSerialPort` | 拖进整个 Qt Core |
| 各平台的 `libserialport` | 多一层 C API 包装，Windows 上还要额外带 DLL |

实际要吃的平台差异只有这些（全部集中在 `src/serial/serial.cpp` 的 ~660 行里）：

| 能力 | Windows | Linux（termios） |
|---|---|---|
| 打开 | `CreateFile("\\\\.\\COMx")` | `open("/dev/ttyXXX", O_RDWR\|O_NOCTTY\|O_NONBLOCK)` |
| 配置 | `DCB` + `SetCommState` | `termios` + `tcsetattr(TCSANOW)` |
| 超时 | 每次调用设 `COMMTIMEOUTS` | `poll()` 等可读/可写 |
| 可读字节数 | `ClearCommError` → `COMSTAT.cbInQue` | `ioctl(FIONREAD)` |
| 清缓冲 | `PurgeComm` | `tcflush(TCIOFLUSH)` |
| 独占 | `dwShareMode = 0` | `ioctl(TIOCEXCL)` |
| 枚举 | 注册表 `HKLM\HARDWARE\DEVICEMAP\SERIALCOMM` | 扫 `/dev/tty{USB,ACM,S,AMA}*` + `/dev/serial/by-id/*` |

## 2. API

```cpp
#include "my_cpp_libs/serial/serial.hpp"

my::serial::Config cfg;
cfg.baud      = 921600;                       // 见 §4 波特率表
cfg.data_bits = 8;
cfg.parity    = my::serial::Parity::None;
cfg.stop_bits = my::serial::StopBits::One;
cfg.flow      = my::serial::Flow::None;

auto opened = my::serial::Port::open("/dev/ttyUSB0", cfg);
if (!opened) { /* opened.status() 里有 errno 与路径 */ }
my::serial::Port& port = opened.value();

std::uint8_t buf[256];
auto n = port.read_some(buf, sizeof buf, std::chrono::milliseconds(100));
// 关键契约：超时返回 0 字节 + Ok，不是错误
if (n && n.value() > 0) { /* 处理 n.value() 个字节 */ }

port.write_all("PING\r\n", 6, std::chrono::milliseconds(100));
auto line = port.read_line('\n', 128, std::chrono::seconds(1));
```

| 接口 | 说明 |
|---|---|
| `Port::open(name, cfg)` | 先 `validate(cfg)` 再开设备；`NotFound` / `Busy` / `IoError` 分开报 |
| `validate(cfg)` | 纯参数校验，不碰设备（可单独用于配置加载时的早期检查） |
| `is_open()` / `name()` / `close()` | `close()` 幂等；析构自动关 |
| `read_some(buf, n, timeout)` | **超时 = 0 字节 + Ok**；`n == 0` 立即返回 0 |
| `write_some(buf, n, timeout)` | 返回实际写出的字节数；超时返回已写部分 + Ok |
| `write_all(buf, n, timeout)` | 循环写；写不完返回 `Errc::Timeout`，消息里带"已写 X/Y" |
| `read_line(delim, max_len, timeout)` | 返回不含行尾的字符串；超时返回已收到的部分 |
| `bytes_available()` | 接收缓冲里的字节数（`FIONREAD` / `cbInQue`） |
| `flush()` | 丢弃收发缓冲（`tcflush` / `PurgeComm`） |
| `native_handle()` | 引出原生 fd / HANDLE，供自己 `poll`/`select`/`WaitForSingleObject` |
| `list_ports()` | 返回 `{name, description}`，按名字排序；空表不是错误 |

### 2.1 为什么 `read_some` 超时不算错误

串口不像 TCP：**"暂时没数据"是常态**。轮询循环里如果每次超时都返回错误，调用方就得
在循环里写 `if (code == Timeout) continue;`，把错误码当成控制流用。
所以这里的约定是：

```cpp
while (running) {
    auto n = port.read_some(buf, sizeof buf, 50ms);
    if (!n) { /* 真正的错误：设备消失/未打开 */ break; }
    if (n.value() == 0) continue;   // 这一轮没数据，继续等
    handle(buf, n.value());
}
```

`my::net` 的 `recv` 超时返回 `Errc::Timeout`，是因为 TCP 的超时通常意味着对端/链路出问题。
**两者的取舍不同，别记混**（两处头文件都写了这条）。

## 3. 怎么测的（没有串口硬件也能验）

| 层 | 覆盖 | 平台 |
|---|---|---|
| 参数校验 / 端口枚举 / 移动语义 | 8 条用例 | 全平台（Windows 上移动语义用例会 skip） |
| 真实收发 | 11 条用例，跑在 **PTY 对**上（含"对端挂断返回 IoError"） | Linux / macOS（Windows 跳过） |

PTY 的做法：`posix_openpt` 造一对伪终端，master 端当"对端设备"，slave 路径交给
`Port::open()` —— 于是 `read/write/poll/FIONREAD/tcflush` 走的是**真实的驱动路径**，
不是打桩。覆盖：往返收发、读超时、行读取、`max_len` 截断、超时返回部分、`bytes_available`
+ `flush`、关闭后再操作报错、对端不读导致 `write_all` 超时、两个端口互不干扰。

Windows 上没法凭空造无名 COM 口（要 com0com 这类驱动），所以那 9 条在 Windows 上
`MYTEST_SKIP`。CI 里它们跑在三个地方：Linux 全组件 job、两个 QEMU job（armv7/aarch64 真跑）。

> 一条经验：串口的 bug 大多在**超时边界**和**部分写**上，不在"正常路径"。
> 所以用例专门盯这两处 —— 比如 `serial_pty_write_all_times_out_when_peer_never_reads`
> 用 64 KB 灌爆 PTY 缓冲，验证的是"绝不能永久阻塞"。

## 4. 波特率

| 平台 | 支持情况 |
|---|---|
| Windows | **任意整数**（`DCB.BaudRate` 本身就接受任意值） |
| Linux | 只支持 termios 的标准档位，见 `standard_bauds()` |

标准档位：`50, 75, 110, 134, 150, 200, 300, 600, 1200, 1800, 2400, 4800, 9600, 19200,
38400, 57600, 115200, 230400, 460800, 500000, 576000, 921600, 1000000, 1152000,
1500000, 2000000, 2500000, 3000000, 3500000, 4000000`（具体可见档位取决于 libc/内核头文件，
代码里逐个 `#ifdef` 保护）。

给非标准值时的行为：**`Errc::InvalidArgument`，消息里列出支持的值**，不静默降级 ——
静默降级会让人对着"通了但不通"的现象查一整天。

> 需要 3 Mbaud 以上或非标准值（如 250000）时的办法是走 `termios2` + `BOTHER`
> （`ioctl(TCSETS2)`）。它要 `<asm/termbits.h>` 且与 `<termios.h>` 冲突，实现上得把这部分
> 单独放一个 TU —— 目前没有需求，没做，列在 §7。

## 5. 板端实践（Zynq）

1. **权限**：`/dev/ttyUSB0` 默认属主是 `root:dialout`，普通用户要 `usermod -aG dialout $USER`。
   打不开时 `open()` 的报错会直接提示这一点（而不是只给一个 `errno=13`）。
2. **别用 `ttyS0` 当数据口**：Zynq 的 `ttyPS0` 通常是调试串口（console），抢它会丢 shell。
   接 FPGA 用 `ttyPS1` 或 USB 转串口（`ttyUSB*`）。
3. **路径稳定性**：`ttyUSB0` 的编号会随插拔顺序变。要写进配置文件就用
   `/dev/serial/by-id/usb-...`（`list_ports()` 会把它们作为带描述的条目一起返回）。
4. **高波特率要开流控**：921600 以上且对端可能来不及收时，配 `Flow::Hardware`（RTS/CTS），
   否则只能靠 `write_some` 的返回值和重试。
5. **`ttyACM` vs `ttyUSB`**：CDC-ACM 设备（很多 MCU 板）是 `ttyACM*`，走的是 USB CDC 类驱动，
   和 `ttyUSB*`（FTDI/CP210x 等）在 termios 行为上基本一致，但 `tcflush` 的时机略不同 ——
   遇到"打开后前几个字节丢了"，先 `flush()` 再开始收。

## 6. 与其它组件配合

```cpp
// 后台收数据：thread 组件 + 一读一写（串口是全双工的）
auto pool = my::thread::ThreadPool::create(2);   // 构造是 create()，不是构造函数
if (pool) {
    (void)pool.value()->submit([&] { /* 收 */ });   // submit 返回 future，别丢它的 [[nodiscard]]
    (void)pool.value()->submit([&] { /* 发 */ });
}

// 落盘：io 组件（原子写，掉电不会留半个文件）。
// write_file 收 string_view，且返回 [[nodiscard]] Status；二进制先 reinterpret_cast
// （这里会拷贝一次，几百 KB 可接受；几 MB 的流式落盘请直接用 ofstream）。
std::string_view chunk(reinterpret_cast<const char*>(buf), n);
if (auto st = my::io::write_file("capture.bin", chunk); !st) {
    // 落盘失败要处理（磁盘满/只读挂载）
}

// 时间戳：time 组件（unix_ms() 给毫秒时间戳，format_utc 要的也是它）
auto ts = my::time::format_utc(my::time::unix_ms());
```

线程安全边界：**同一个 Port 只让一个线程读、一个线程写**，库内部不加锁（和 `my::net` 一致）。

## 7. 已知限制

- **Linux 非标准波特率**不支持（见 §4）；
- **没有异步/事件回调**：要事件驱动就用 `native_handle()` 自己 `poll`/`WaitForSingleObject`；
- **RS-485 半双工方向控制**没做（需要 GPIO 控制 DE/RE，属板级）；
- **Windows 上的收发用例**要装虚拟串口驱动才能真跑，因此 CI 里只在 Linux/QEMU 验证；
- `read_line` 逐字节读，只适合命令行式协议（AT 指令、NMEA）。收二进制帧请用 `read_some`
  自己攒包 —— 逐字节读在高波特率下会多几倍的 syscall。
